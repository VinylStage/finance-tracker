# finance-tracker UI/UX 개편 설계 문서

**작성일**: 2026-07-26
**대상 커밋**: `develop` (v0.6.0 기준, 클론 확인 완료)
**목적**: 개인용 로컬 가계부 앱을 "서비스로 판매 가능한 수준"으로 개편하기 위한 UX/UI 리서치 종합 및 구체적 설계 방향 제시. 이 문서는 실행 백로그(GitHub 이슈)의 근거 문서 역할을 한다.

---

## 0. 요약 (TL;DR)

현재 finance-tracker는 **기능적으로는 이미 상당히 성숙한 개인 재무관리 앱**이다(거래 CRUD, 예산 대비 실적, 카테고리 자동제안, 반복거래 자동등록, 할부/리볼빙/부채/저축 전용 관리, 감사 이력까지). UI도 Tailwind 기반으로 일관된 카드/컬러 언어를 쓰고 있어 "방치된 개인 프로젝트" 수준은 아니다.

그러나 리서치와 코드 검토 결과, **"판매 가능한 서비스"로 가기 위해 막고 있는 것은 새 기능이 아니라 다음 5가지 구조적 갭**이다.

1. **정보구조(IA) 부재** — 10개 탭이 전부 평평하게 나열되고, URL 라우팅이 없어 새로고침·뒤로가기·북마크·공유가 전부 깨진다.
2. **행동경제학적 설계가 없다** — 예산 초과 알림, 저축 목표 진행바, 카테고리 구분이 전부 "정보 표시"에 머물러 있고 "행동을 바꾸는 설계"가 아니다.
3. **접근성 결함** — 수입/지출을 색상으로만 구분(WCAG 1.4.1 위반), 거래 테이블이 모바일에서 컬럼을 숨겨 정보를 손실시킨다.
4. **온보딩/신뢰 신호 부재** — 첫 실행 시 설명 없이 빈 화면, "이 앱이 내 재무데이터를 어떻게 다루는지"에 대한 어떤 신호도 없다.
5. **서비스화 전제조건 미비** — 인증 없음, 멀티유저 개념 없음. 기존 독립 감사 보고서(FND-01 등)가 이미 "루프백 바인딩만으로는 브라우저발 공격을 못 막는다"를 실증한 상태라, 서비스화 이전에 반드시 선결돼야 하는 보안 항목이다.

아래에서 리서치 근거 → 화면별 설계 방향 → 실행 백로그 순으로 정리한다.

## 1. 현재 상태 진단 (코드 기반)

`client/src/` 코드를 직접 열어 확인한 사실 기준:

- **네비게이션**: `App.jsx`가 `useState('dashboard')`로 페이지를 전환하는 완전한 SPA-in-a-div 구조. React Router 등 URL 기반 라우팅이 전혀 없다. 대시보드/거래입력/기간비교/할부/리볼빙/부채/적금/시뮬레이터/설정/가이드 **10개 탭이 전부 동일 위계로 가로 스크롤 바에 나열**된다.
- **대시보드**(`Dashboard.jsx`, 534줄): 요약 카드 3개(수입/지출/가용현금) → 반복거래 확인 → 카테고리 파이차트+범례 → 예산 대비 실적(진행바) → 카테고리별 지출 비교(막대/라인 토글) → 흐름 분석(영역차트, 일/주/월/연) → 순자산 추이 → 부채 잔액 추이 → Top5 가맹점/카테고리. **한 화면에 9개 섹션이 순차 노출**되며 접기/우선순위 조절 장치가 없다.
- **거래 목록**(`Transactions.jsx` + `TransactionList.jsx`): 연도 탭 + 월별 아코디언 + `<table>`. 모바일에서는 `hidden md:table-cell`, `hidden sm:table-cell`로 가맹점·결제수단 컬럼을 **숨김 처리**(제거가 아니라 비표시라 스크린리더도 접근 불가하진 않지만, 시각적으로 정보가 사라짐).
- **색상 구분**: 수입은 `text-emerald-600`, 지출은 `text-slate-800`+`-` 부호, 카테고리 대분류는 `TYPE_COLOR` 맵으로 6색 텍스트 색상만 사용. 부호(`+`/`-`)는 금액 앞에 있지만 카테고리 대분류 구분은 **색상 단독**.
- **폼**: `TransactionForm.jsx`는 페이지 내 인라인 확장 폼(모달 아님), 가맹점 입력 시 카테고리 자동제안(완전일치/부분일치 배지)이 이미 구현되어 있음 — 이 부분은 이미 좋은 패턴.
- **온보딩**: 없음. `README.md`에 따르면 첫 실행 시 기본 카테고리/결제수단만 자동 시드되고, 화면상 설명은 `Guide` 탭(마크다운 렌더)에 위임되어 있다 — 그런데 `Guide`는 별도 탭이라 처음 켰을 때 강제로 보여주지 않는다.
- **인증**: 없음. `docs/ARCHITECTURE.md`가 "단일 사용자, 로컬 전용"을 설계 원칙으로 명시. 이미 존재하는 `docs/audit/AUDIT_REPORT_2026-07.md`가 "루프백 바인딩은 다른 기기 접근은 막지만 같은 기기의 브라우저가 방문한 임의 웹사이트로부터의 접근은 못 막는다"는 것을 CSRF 실증(FND-01, 현재 closed)으로 이미 증명한 바 있다 — 서비스화 논의에서 이 전제를 다시 검토해야 한다는 근거가 이미 레포 안에 있다.
- **디자인 시스템**: 별도 토큰 레이어 없음. Tailwind v4(`@import "tailwindcss"`)를 쓰지만 `index.css`에는 바디 기본 스타일만 있고, 인디고/슬레이트/에메랄드/로즈 등 색상이 컴포넌트마다 하드코딩된 유틸리티 클래스로 흩어져 있다.

## 2. 리서치 종합 (근거 + 출처)

세 갈래로 웹 리서치를 진행했다.

### 2.1 업계 벤치마크 (Mint / YNAB / 토스 / 뱅크샐러드)

- **YNAB**은 소프트웨어 사용법이 아니라 "제로베이스 예산이라는 사고방식 전환" 자체를 온보딩에서 가르친다.
- **토스**의 제품 원칙은 "Simplicity"이며 하위 원칙으로 "Casual Concept", "Minimum Features"를 명시한다.
- **뱅크샐러드**는 리서치 중심 설계를 강조하며 최근 '라이프' 영역으로 확장 중이다.
- **Mint**는 계정 개요 화면의 과밀함이 이탈의 주요 원인으로 지적됐다.
- **IA 원칙**: 10개 이상 플랫 탭은 모바일에서 관리 불가능한 수준이 된다(NN/g).

### 2.2 행동경제학/심리학

- **Mental Accounting**(Thaler, 1999), **Loss Aversion**(Kahneman & Tversky, 1979), **Nudge Theory**(Thaler & Sunstein, 2008), **Goal-Gradient Effect**(Kivetz et al., 2006), 정보 과부하(대시보드 사용자 46.7%), **Fogg Behavior Model**(B=MAP).

### 2.3 데이터 시각화 / 신뢰 / 서비스화

- 파이차트 5~6개 초과시 판독성 급락, 색상 단독 정보전달 WCAG 위반, 신뢰 마이크로카피의 효과, empty state의 이탈 방지 효과, 멀티테넌시 데이터 격리, 다크모드는 옵트인 권장.

(전체 근거/출처 목록은 리서치 세션 원본에 있으며 필요시 재요청 가능)

## 3. 설계 원칙 (finance-tracker 맞춤 5원칙)

1. 한 화면, 한 질문
2. 색은 보조, 기호가 본체
3. 넛지는 시점이 전부다
4. 마찰 제거가 곧 기능이다
5. 신뢰는 설계 디테일에서 나온다

---

## 4~6. 화면별 개편 방향 / 우선순위 / 실행 백로그

위에서 전달한 이슈 1~15와 동일한 내용이 화면별로 매핑되어 있음 (섹션 4.1 IA/네비게이션, 4.2 대시보드, 4.3 거래내역, 4.4 색상/접근성, 4.5 온보딩/서비스화, 4.6 디자인토큰). 우선순위: P1=서비스화 구조적 전제조건(IA/라우팅, 인증설계), P2=리텐션/행동변화 직접기여, P3=완성도/차별화.
