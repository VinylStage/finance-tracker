# 0007: 감사로그는 트리거로 잡고, 의미 라벨만 애플리케이션이 얹는다

관련: #296(결정 이슈), 구현 #297 · #298 · #299 · #300 · #301, 후속 #346(재생성 책임 이관)

## Context and Problem Statement

M12 가 감사로그와 1단계 실행취소를 들여온다. 그 전에 **쓰기를 어디서 잡을 것인가**를 정해야 했다. 이 결정이 M12 나머지 이슈(#297~#301)의 형태를 전부 바꾸므로 코드보다 먼저 확정했다.

아래는 **2026-08-03 결정 시점의 실측**이다. 결정의 근거로 남기는 값이므로 이후 코드가 늘어도 소급해 고치지 않는다.

| 항목 | 값 |
|---|---|
| 쓰기 엔드포인트 | 38개 / 14개 라우트 파일 |
| `db.prepare` 호출 지점 | 약 130곳 |
| DAO·리포지토리 계층 | **없음** — 라우트가 `db` 싱글턴을 직접 씀 |
| 드라이버 | better-sqlite3 13 (**동기**) |
| `ON DELETE CASCADE` | 없음 |

**DAO 계층이 없다는 게 핵심 제약이다.** 훅을 걸 중간 지점이 존재하지 않는다.

배경이 하나 더 있다. 이 저장소는 **과거 실거래 2,212건이 유실된 사고**를 겪었다. 감사로그의 가치는 완전성에 있다 — 부분 로그는 "아무 일도 없었다" 와 "그 테이블은 로깅을 안 한다" 를 구별하지 못해 증거가 되지 못한다.

## Considered Options

### A. SQLite 트리거

테이블별 `AFTER INSERT/UPDATE/DELETE` 트리거가 `OLD`/`NEW` 행을 JSON 으로 `audit_log` 에 밀어넣는다.

- 앱 코드가 무엇을 하든 **빠뜨릴 수 없다.** 대량 삭제·임포트·수동 SQL 까지 전부 잡힌다
- 누가 했는지(actor)를 트리거가 모른다 → 컨텍스트 전달 수단이 따로 필요하다
- 테이블이나 컬럼이 늘면 트리거를 다시 만들어야 한다

### B. `db` 래퍼 / Proxy

`src/db/init.js` 가 내보내는 `db` 를 감싸 `prepare()` 를 가로챈다.

- 앱 컨텍스트(actor, 요청)를 그대로 쓸 수 있다
- 130곳 호출부를 안 건드려도 된다
- `UPDATE`/`DELETE` 의 **변경 전 값**을 알려면 SQL 을 파싱해 대상 행을 미리 `SELECT` 해야 한다

### C. 엔드포인트마다 명시적 호출

각 핸들러에서 `recordChange(...)` 를 부른다.

- 의도를 정확히 남길 수 있다 — "할부 완료처리" 같은 의미 단위
- **38곳을 손대야 하고, 앞으로 추가되는 엔드포인트마다 잊으면 그대로 구멍이다**
- M8·M10·M11 이 새 엔티티를 계속 들여온다(#274 카드상품, #285 대출유형, #288 계좌) → 마일스톤마다 세금

## Decision Outcome

**A + C 혼합을 채택한다** (확정 2026-08-03).

**캡처는 A(트리거)가 전담하고, C 는 의미 라벨만 얇게 얹는다.**

- 트리거가 "무엇이 어떻게 바뀌었나"(`before_json` / `after_json`)를 빠짐없이 잡는다
- 라우트는 "이건 무슨 작업이었나"(`action_label`)만 컨텍스트에 얹는다

**라벨을 안 붙여도 로그는 남는다.** 빠뜨려도 구멍이 나지 않는 구조 — 이것이 채택 이유의 전부다. C 단독안이 탈락한 지점이 정확히 여기다. C 는 빠뜨리면 그 쓰기가 로그에 아예 없고, 없다는 사실조차 드러나지 않는다.

### B 를 기각한 이유

**임의 WHERE 절 파싱이 이 앱의 유일한 정확성 근거가 되는 게 위험하다.**

`transactions.js` 하나에만 `db.prepare` 가 26곳이고 쿼리 형태가 제각각이다. 파서가 못 다루는 형태가 하나 생기면 그 경로의 before 값이 조용히 빈다 — 그리고 그 사실은 감사가 필요해진 시점에야 드러난다. 정확성 근거를 "우리가 우리 SQL 을 다 커버했는가" 에 두는 것보다, SQLite 엔진이 실제 행 변경 시점에 주는 `OLD`/`NEW` 에 두는 편이 낫다.

### C 단독을 기각한 이유

38곳을 손대는 비용 자체는 문제가 아니다. **새 엔드포인트가 추가될 때마다 같은 세금을 계속 낸다는 점**이 문제다. 이 사이클(M6~M13)만 해도 새 엔티티가 셋 들어온다.

## 전제 — 이 결정이 성립하는 조건

**better-sqlite3 는 동기이고, 이 앱은 단일 프로세스·단일 커넥션이다.**

트리거는 JS 상태를 볼 수 없으므로 actor 와 `action_id` 를 단일 행 테이블 `_audit_context` 에서 읽는다. 애플리케이션이 쓰기 직전에 그 행을 갱신한다. **요청 처리 중간에 다른 요청의 쿼리가 끼어들 수 없기 때문에** 성립하는 방식이다.

비동기 드라이버였다면 쓸 수 없다. 다음 중 하나라도 들어오면 이 설계를 다시 봐야 한다.

- **커넥션 풀** — 두 요청의 쓰기가 겹치면 `_audit_context` 가 서로를 덮어쓴다
- **워커 스레드 / 다중 프로세스** — 같은 이유
- **비동기 드라이버로 교체**

그때의 대체 수단은 `AsyncLocalStorage` 다. 컨텍스트를 요청 단위로 격리하고, 트리거에 넘길 값은 쓰기 직전에 동기적으로 밀어넣는다. `src/utils/auditContext.js` 가 이 전제를 주석으로 들고 있다.

### 트리거가 굳는 성질

트리거는 **생성 시점의 테이블 목록과 컬럼 목록을 굳힌다.** 컬럼을 하드코딩하지 않으려고 `PRAGMA table_info` 로 읽어 생성하지만, 그건 생성 시점의 이야기다. 나중에 테이블이나 컬럼이 늘면 재생성해야 한다.

"테이블을 만든 마이그레이션 작성자가 재생성을 기억한다" 는 방식은 사람의 기억에 걸린 보장이라 언젠가 샌다. **마이그레이션 러너가 체인을 다 적용한 뒤 한 번 재생성하도록 옮겼다(#346, PR #356).** `018-add-accounts.js` 가 직접 부르던 호출은 그때 제거했다.

## 구현 결과 (2026-08-04 실측)

| | |
|---|---|
| 감사 대상 테이블 | 18개 |
| 감사 트리거 | 54개 (18 × ins/upd/del) |
| 제외 | `audit_log`(무한 루프) · `_audit_context` · `schema_migrations`(데이터 변경이 아님) · `sqlite_sequence` |
| 캡처 누락 감시 | `test/audit-coverage.test.js` — 대상 테이블에 트리거가 없으면 실패 |
| 재생성 책임 | `runMigrations()` (#346, PR #356). `019-card-benefits.js` 에 중복 호출이 하나 남아 있다 — PR #360 대기 |

actor 구분은 `runAs(actor, fn)` 로 8곳에서 쓰고 있다 — 임포트(`import`) 5곳, 시스템 자동처리(`system`) 3곳. 사용자가 조회만 했는데 데이터가 바뀌는 경로(#205 의 만료 할부 자동 완료)를 `user` 로 찍으면 실행취소가 엉뚱한 것을 되돌리기 때문이다.

**`action_label` 은 아직 프로덕션 경로에서 쓰이지 않는다.** `setAuditLabel()` 이 있고 테스트도 있지만 라우트에서 부르는 곳이 없다. 감사 이력 화면(#301)이 표시할 라벨이 지금은 전부 비어 있다는 뜻이다. **이것이 설계대로다** — 라벨은 선택이고, 없어도 로그에는 구멍이 없다. 다만 화면이 붙는 시점(#301)에 라벨을 붙일 작업 단위를 정해야 실제 가치가 난다.

## Consequences

### 좋아지는 것

- **빠뜨릴 수 없다.** 라우트를 새로 만들면서 로깅을 잊어도 잡힌다. 임포트·복원 같은 대량 경로도 자동으로 걸린다
- 새 엔드포인트를 추가할 때 감사 관련해 할 일이 없다
- `before_json` / `after_json` 이 실제 행 값이라, 실행취소(#300)가 그 값을 그대로 역적용할 수 있다

### 비용

- **쓰기마다 `audit_log` 삽입이 하나씩 는다.** 대량 임포트는 행 수만큼 로그가 쌓인다 — 행수 상한과 정리가 필요하다(#297)
- 트리거는 SQL 문자열로 생성되므로 **디버깅이 앱 코드보다 어렵다.** 실패가 SQLite 에러로 나온다
- 테이블·컬럼 변경 때마다 재생성이 필요하다. 그 책임은 러너로 옮겼지만(#346), 재생성 자체는 사라지지 않는다

### 지켜지지 않을 수 있는 지점

- **`_audit_context` 갱신을 빠뜨린 경로**는 기본값 `system` 으로 찍힌다. 로그는 남지만 실행취소 후보에는 오르지 않는다. 안전한 쪽으로 틀리게 설계했으나, 사용자 작업이 `system` 으로 찍히면 되돌릴 수 없다
- **`runAs` 의 복원**은 `finally` 로 보장하지만 **동기 함수만 받는다.** 비동기를 넘기면 복원 시점이 어긋나 다음 작업의 actor 가 오염된다
- 트리거를 우회하는 유일한 경로는 **`PRAGMA` 로 트리거를 끄거나 DB 파일을 직접 여는 것**이다. 앱 밖의 일이므로 이 설계가 막지 않는다

## 재검토 트리거

- 커넥션 풀·워커 스레드·비동기 드라이버 중 하나라도 도입되면 — 위 "전제" 가 깨진다
- `audit_log` 크기가 실사용에 부담이 되면 — 상한·보존기간 정책을 다시 본다
- 트리거 재생성이 누락돼 캡처에 구멍이 난 사례가 실제로 생기면 — `test/audit-coverage.test.js` 가 잡지 못한 경로가 있다는 뜻이다
