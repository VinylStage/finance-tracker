# 0008: 데이터를 고치는 동작은 프리뷰와 확인 없이 실행하지 않는다

관련: #307(공통 원칙 이슈), 선행 #289(`settlement` 재분류에서 최초 수립), 적용 대상 #269 · #302 · #306 · #300 · #297, 경계 사례 #279

## Context and Problem Statement

M6~M13 계획 사이클에 **기존 데이터를 대량으로 고치는 기능**이 여럿 들어왔다.

아래 규모는 **2026-08-03 오전 실측**이다. 이 결정의 근거로 남기는 값이므로 이후 데이터가 늘어도 소급해 고치지 않는다. 실제 착수 시점의 건수는 각 이슈에서 다시 잰다.

| 이슈 | 동작 | 규모 |
|---|---|---|
| #269 | 할부 수정 시 파생 거래 전체 재생성 | 회차 수만큼 삭제 + 재삽입 |
| #302 | 카드 재매핑(B안) | 278건 — 하나카드 260, 신한 18 |
| #306 | 결제수단 분류 마이그레이션, `미상` 일괄 지정 | 카드 거래 447건 |
| #289 | `settlement` 재분류 | 전체 거래 |
| #300 | 실행취소 역적용 | 작업 그룹 크기만큼 |
| #297 | 감사로그 행수 상한 초과분 삭제 | 상한 설정에 따름 |

이 저장소는 **과거 실거래 2,212건이 유실된 사고**가 있었다. 조용한 대량 변경은 같은 범주의 위험이다 — 실행 시점에 아무 일도 일어나지 않은 것처럼 보이고, 사용자가 이상을 알아채기까지 시간이 걸린다.

#289 를 설계하며 "자동 변환 금지, 미리보기 후 확인" 을 세웠으나 **그 이슈 안의 규칙으로만 존재**했다. 같은 성질의 기능이 다섯 개 더 생기면서 각자 다르게 처리될 위험이 생겼다.

또 하나. M12(#300)가 실행취소를 붙이므로 "되돌릴 수 있으니 괜찮다" 는 반론이 가능하다. 그러나 **사용자가 무엇이 바뀌었는지 모르면 되돌릴 판단 자체를 하지 못한다.** 프리뷰는 실행취소의 대체재가 아니라 전제다.

## Considered Options

### A. 각 이슈가 알아서 처리

지금까지의 상태. #289 만 규칙을 갖고 나머지는 미정.

기능마다 확인 수준이 달라지고, 새 기능이 추가될 때 기준이 없다.

### B. 되돌리기(M12)에 의존하고 프리뷰는 생략

구현이 가볍다. 실행취소가 있으니 실수해도 복구 가능하다.

그러나 위에 적은 이유로 성립하지 않는다. 되돌리려면 먼저 **잘못됐다는 걸 알아야** 한다. 260건이 조용히 바뀌면 알아챌 계기가 없다.

### C. 모든 쓰기에 확인을 받는다

가장 안전하지만 앱을 쓸 수 없게 만든다. 거래 하나 입력에 확인창이 뜨면 가계부의 기본 동작이 망가진다.

### D. 대량·구조 변경에만 2단계를 강제한다

프리뷰(DB 불변) → 확인 → 실행. 한 건씩 하는 CRUD 는 제외한다.

## Decision Outcome

**D 를 채택한다.**

기존 데이터를 고치는 동작은 두 단계로 나눈다.

1. **프리뷰** — 무엇이 몇 건, 어떻게 바뀌는지 계산해 보여준다. **이 단계는 DB 를 바꾸지 않는다**
2. **실행** — 사용자가 확인한 뒤에만 쓴다

프리뷰가 보여야 할 것:

- **건수** — 몇 건이 영향받는가
- **전 → 후** — 대표 사례 몇 건의 실제 값 변화. 숫자만으로는 판단이 안 된다
- **부작용** — 삭제되는 것, 새로 생기는 것, 금액 합계 변화
- **되돌릴 수 있는가** — 실행취소 대상인지, 백업 복원이 필요한지

### 적용하지 않는 것

- **사용자가 한 건씩 직접 하는 CRUD.** 단 되돌릴 수 없는 동작에는 확인을 받는다(#295 의 완료처리가 그 사례 — 확인이 없어서 실제로 사고가 났다)
- **읽기 전용 계산.** #276 카드 추천처럼 값을 제안만 하고 쓰지 않는 기능

### 경계 사례 — 자동 생성 (#279)

서버 기동 시 반복거래 catch-up 은 기존 데이터를 고치는 게 아니라 **새로 만든다.** 한 달을 안 켰다가 켜면 한 달치가 한 번에 생긴다.

**사전 확인 없이 자동 생성하되, 결과를 요약으로 알리고 실행취소로 되돌릴 수 있게 한다.** 반복거래는 사용자가 규칙을 미리 등록해 "자동으로 생겨라" 라고 지시한 것이므로, 앱을 열 때마다 확인을 받으면 규칙의 취지가 사라진다.

즉 **조용히 넘어가지 않되, 흐름을 막지도 않는다.**

## Consequences

### 좋아지는 것

- 대량 변경 전에 사용자가 규모를 안다. 260건이 바뀐다는 사실이 실행 전에 보인다
- 기능마다 다르게 처리되던 것이 하나의 기준을 갖는다
- 새 기능이 추가될 때 판단 기준이 있다 — "기존 데이터를 고치는가"

### 비용

- **기능마다 프리뷰 계산 경로를 따로 만들어야 한다.** 실행 로직과 프리뷰 로직이 갈라지면 둘이 어긋날 수 있다 — 같은 계산을 공유하고 쓰기 여부만 분기하는 구조가 필요하다
- 화면이 늘어난다. 프리뷰 표시는 UI 작업이다
- 사용자 동선이 한 단계 길어진다

### 지켜지지 않을 수 있는 지점

- **API 를 직접 호출하면 프리뷰를 건너뛸 수 있다.** 화면에서만 막고 엔드포인트가 열려 있으면 원칙이 반쪽이 된다. 각 이슈의 인수 기준에 우회 경로 확인을 넣었다
- **프리뷰가 조용히 쓰기를 하면 원칙이 무의미해진다.** "프리뷰만 실행하고 데이터가 그대로인지" 를 테스트로 고정한다

## 재검토 트리거

- 프리뷰 로직과 실행 로직이 어긋나 잘못된 프리뷰가 나온 사례가 생기면
- 사용자가 확인 단계를 습관적으로 넘기는 것이 관찰되면 — 그때는 확인의 위치나 형태를 다시 본다
