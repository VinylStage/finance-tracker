# 0006: 시각 디자인 토큰 체계 전면 교체

관련: Claude Design 프로젝트 「자산관리 앱 리뉴얼 방향안」 handoff (DESIGN_SPEC.md / MOTION_SPEC.md / TAILWIND_MAPPING.md / index.css), 선행 #190(시맨틱 토큰 도입) · #191(색상 단독 전달 제거) · #193(예산 3단계) · #201(다크모드)

## Context and Problem Statement

기존 토큰 체계(#190)는 Tailwind 기본 팔레트를 의미 이름으로 감싼 것이었다. 값이 팔레트
그대로라 치환 전후 렌더가 같았고, 그래서 "이름은 의미를 말하는데 값은 아무것도 결정하지
않은" 상태로 남았다. 한 화면에 hue 가 10개였다 — 카테고리 6색(emerald/rose/orange/red/
yellow/blue) + 의미색 4색(income emerald, expense rose, warning amber, accent indigo).
이 색들이 공유하는 축이 없어 각자 따로 떠 보였다.

외부 디자인 도구에서 리뉴얼안이 나왔고 handoff 문서 4종이 딸려 왔다. 그대로 적용할지
검토하는 과정에서 문서 내부의 모순 3건과, 문서가 주장하는 AA 통과가 실측과 다른 지점이
드러났다.

## Decision

토큰 이름을 유지하지 않고 신규 체계로 전면 교체한다. 값·이름·의미를 한 번에 바꾸는 대신
기존 이름을 남겨두면, 이름이 가리키는 의미와 실제 값이 또 한 번 어긋난다 — #190 이 만든
문제를 반복하게 된다.

원칙은 **hue 2개**다. 액센트 블루(액센트·링크·수입·차트·선택 상태)와 손실 레드(지출·
초과·삭제). 그 외 전부 무채색. 카테고리에는 색을 배정하지 않고 아이콘 모양으로 구분한다.

이하 세 항목은 handoff 원안과 다르게 결정한 것이다.

### (a) 예산 정상 단계(80% 미만)는 액센트를 유지한다

원안 §5.2-3 은 3단계를 "정상(액센트) / 주의 80%+ / 초과 100%+" 로 규정한다. 이것이 같은
문서 §1.3 의 "액센트 블루로 버튼을 칠하면 화면에 파란 덩어리가 남는다" 와 충돌한다고 보고
중립색으로 내리는 안을 검토했다.

**기각한다.** 두 가지 근거다.

1. §1.3 의 금지 대상은 **버튼**이다. 같은 문서 §1.1 은 액센트의 용처에 "차트" 를 명시적으로
   포함한다. 예산 막대는 h-1.5 짜리 데이터 표현 요소이지 액션 면이 아니다.
2. 기존 구현이 이미 액센트다. `BUDGET_TONE.normal.bar` 는 교체 전에도 `bg-accent-bar`
   였다. #193 주석의 "중립" 은 색이 아니라 **프레이밍**(자원 프레이밍 vs 손실 프레이밍)을
   가리키는 말이고, 그 자리의 중립은 막대가 아니라 **문구 색**(`text-ink-muted`)이 맡고
   있었다.

즉 원안과 기존 구현이 이 지점에서 이미 일치했다. 바꿀 이유가 없다.

경계 정의도 #193 그대로 유지한다 — `ratio > 1` 이라야 초과이므로 **소진율 100.0% 는
'주의'** 다. 원안 §5.2-3 의 "초과 100%+" 는 `>` 인지 `>=` 인지 불명확한데, 기존 정의가
더 좁게 명시돼 있으므로 그쪽을 정본으로 둔다.

### (b) warn 과 pending 을 서로 다른 hue 로 분리한다

`TAILWIND_MAPPING.md` §2.11 은 이렇게 쓴다 — "예산 주의(80%)에 pending 을 쓰지 않는다.
둘을 섞으면 '아직 안 쓴 돈' 과 '너무 많이 쓴 돈' 이 같은 색이 된다."

그런데 원안 `index.css` 의 실제 값이 동일했다.

```
warn-fill #D9A63C  ==  pending-fill #D9A63C
warn-text #96650F  ==  pending-text #96650F
```

문서가 막으려던 상황이 값 수준에서 그대로 발생해 있었다. 덧붙여 `DESIGN_SPEC.md` §1.1 과
`index.css` 주석은 주의색을 "레드 계열의 옅은 단계 — 노랑을 쓰지 않는다" 로 서술하는데
`#D9A63C` 는 hue 41° 의 앰버다. 같은 값을 pending 쪽에서는 "화면의 유일한 따뜻한 색" 이라
부른다. 서술이 서로 모순이고, hue 2개 원칙도 실제 값 기준으로는 3개였다.

**warn 을 레드 계열로 재조정하고 앰버는 pending 에 남긴다.** 서술과 값을 일치시키는
방향이고, "약한 위험 → 강한 위험" 이 같은 hue 안에서 이어진다.

| 토큰 | 원안 | 결정 | hue | 실측 대비 |
|---|---|---|---|---|
| `--color-warn-text` | `#96650F` | `#B4442A` | 11° | 흰 5.52 · 페이지 5.05 |
| `--color-warn-fill` | `#D9A63C` | `#CF5A34` | 15° | 트랙 3.59 (비텍스트 3:1) |
| `--color-warn-tint` | (없음) | `#FBEDE7` | — | warn-text 얹어 4.83 |
| `--color-pending-text` | `#96650F` | `#85590C` | 38° | 흰 6.12 · tint 5.39 |
| `--color-pending-fill` | `#D9A63C` | `#AD7E23` | 41° | 트랙 3.20 |

warn 은 loss(348°)와 pending(41°) 사이에 놓이되 loss 쪽에 가깝다. pending 값을 함께 내린
것은 hue 때문이 아니라 대비 때문이다 — 원안 값은 막대로 쓰면 트랙 위 1.96, tint 위 글자
4.44 로 둘 다 미달이었다.

### (c) 대비값은 실측만 정본으로 삼는다

원안은 같은 조합에 문서마다 다른 수치를 적어 두었다. `#96650F` on 흰 배경이 한 곳에서는
5.04, 다른 곳에서는 5.25 다. 다크 액센트는 6.00 / 5.25 두 값이 돌아다니고, 다크 기본버튼
글자색은 hex 자체가 `#101820` 과 `#12161C` 로 갈린다.

WCAG 2.x 상대휘도 공식으로 전부 재계산하고 **실측값만 남긴다.** 문서 수치는 채택하지
않았다. 계산 결과 원안이 놓치고 있던 **AA 미달 5건**이 추가로 나왔다.

| 항목 | 원안 값 | 문제 | 결정 |
|---|---|---|---|
| `--color-caption` | `#5F7387` | 흰 위 4.90 은 통과하나 페이지 위 4.47 · 가라앉은 면 위 4.32 미달 | `#56697C` (최악 배경 5.00) |
| 다크 caption | `#7E8B9A` | 카드 위 4.76 통과, 컨트롤 면 위 4.17 미달 | `#8A97A6` (최악 4.87) |
| `--color-pending-text` | `#96650F` | tint 위 4.44 미달 | `#85590C` (5.39) |
| `--color-pending-fill` | `#D9A63C` | 막대로 쓰면 트랙 위 1.96 미달 | `#AD7E23` (3.20) |
| `--color-heat-3-on` | `#0C1F38` | 4.51 로 여유 없음 | `#08192F` (4.80) |

caption 을 최악 배경 기준으로 올린 이유는 §1.2 와 맞물린다 — 카테고리 구분이 아이콘 모양
하나에 걸리므로, 그 아이콘 색이 화면에서 가장 약한 요소가 되면 안 된다.

한 가지는 원안의 **결론이 맞고 근거만 틀렸다.** 흰 글자 on `--color-brand-fill` 을 3.71 로
적고 "버튼 배경에 쓰지 않음" 이라 결정했는데, 실측은 4.39 다. 그래도 본문 AA(4.5)에는
못 미치므로 결정 자체는 유지한다.

## Consequences

- 기존 6단계 잉크 스케일(ink~ghost)이 3단계(ink/body/caption)로 접힌다. 단계 사이 차이가
  읽히지 않아 위계로 기능하지 못하던 구간이 사라진다. 대신 `text-ink-subtle` 과
  `text-ink-faint` 를 나란히 써서 만들던 미세한 층은 없어진다.
- 수입이 초록에서 블루로 옮겨간다. 부호(+/−)와 방향 아이콘(▲/▼)이 이미 방향을 전달하므로
  (#191) 색만으로 전달하던 정보는 없고, hue 가 하나 줄어든다.
- 카테고리 팔레트(무지개 10색)가 사라진다. 카테고리별 지출 랭킹의 색상 점은 순번 숫자로
  대체했다 — 점은 카테고리마다 hue 를 배정해야 성립하는 장치라 카테고리가 늘면 무너진다.
- 차트 색이 하드코딩 hex 에서 토큰 `var()` 참조로 바뀌어 다크모드에서 함께 전환된다.
  기존에는 41곳이 라이트 팔레트 hex 로 고정돼 있어 다크에서 그대로 남았다.
- `@theme` 이 아니라 `@theme static` 을 쓴다. 기본 `@theme` 은 유틸리티가 참조하지 않는
  변수를 출력에서 지우는데, 차트 색은 Recharts 의 fill/stroke 속성에 `var()` 문자열로
  들어가서 Tailwind 가 사용 사실을 알 수 없다. 그대로 두면 히트맵·Sankey·모션 토큰 11개가
  CSS 에서 통째로 사라진다(실측 확인).

## 남은 작업

이 ADR 의 범위는 토큰 체계와 색 원칙 적용까지다(#240). handoff 의 화면별 결정 중 신규
컴포넌트를 요구하는 항목은 개별 이슈로 쪼개 후속으로 남긴다.

| 이슈 | 항목 | 현재 상태 |
|---|---|---|
| #241 | 자금흐름 Sankey | 집계 모듈 `lib/cashFlow.js` 완료, 차트 남음 |
| #242 | 일별 지출 강도 히트맵 | 계산 유틸 `lib/heatmap.js` 완료, 컴포넌트 남음 |
| #243 | 흐름 분석 차트 유형 분리 | 미착수 |
| #244 | 이모지 → 인라인 SVG + 폰트 self-host | 미착수 |
| #245 | 설정 앵커 목차 | 미착수 |
| #246 | 모바일 탭바 재구성 | 미착수 (#244 의존) |

두 모듈을 먼저 만든 것은 차트보다 **판단이 먼저 굳어야 하는 부분**이기 때문이다.
`cashFlow.js` 는 "수입과 미분류를 갈래로 세지 않는다", "지출이 수입을 넘겨도 남은 돈은
음수가 아니라 0 이다", "비율의 분모는 수입이 아니라 실제 그려지는 총량이다" 같은 결정을
담고 있고, 이것이 데스크톱 Sankey 와 모바일 스택 바 양쪽의 정본이 된다.

### 폰트와 아이콘 — 신규 의존성 없이 간다

CSP 가 `default-src 'self'` 이고 `font-src` 지시자가 없어 CDN 로드가 차단된다. air-gapped
운영 환경 전제상 CDN 자체가 맞지 않으므로, 폰트 npm self-host / 인라인 SVG / 현행 유지
세 선택지 중 **신규 npm 의존성 0개** 방향으로 확정했다(#244).

- 아이콘 13종은 **인라인 SVG** 로 직접 넣는다. `currentColor` 로 그려 토큰 색을 상속받게
  하고, 텍스트 이름이 항상 함께 나오므로 `aria-hidden` 은 유지한다(#191 의 판단을 잇는다).
- Pretendard 는 **한글 subset woff2** 를 `client/public/fonts/` 에 두고 `@font-face` 로
  붙인다. full variable 은 약 1.3MB 라 바이너리를 최소로 두는 이 저장소 성격에 맞지 않는다.
  OFL-1.1 이므로 재배포 가능하고 라이선스 파일을 같이 넣는다.
- 그때까지 `--font-sans` 는 Pretendard 를 앞에 두고 시스템 폰트로 폴백한다. 파일이 붙으면
  토큰 수정 없이 그대로 동작한다.

카테고리 **색** 제거는 이 ADR 에서 이미 끝났다. #244 는 아이콘 모양만 다룬다.

### 알려진 예외

`--color-line-strong` 의 WCAG 1.4.11 미달은 개선이지 퇴행이 아니므로 알려진 예외로 남긴다
(근거는 `docs/design/DESIGN_TOKENS.md`). 감사 사이클에서 같은 지점을 다시 파헤치지 않도록
예외 원장 등재를 #247 로 걸어 두었다.
