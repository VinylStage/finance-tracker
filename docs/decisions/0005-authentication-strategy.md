# 0005: 인증·세션 전략 — 서비스 전환 대비

관련 이슈: #189 (선행: 독립 감사 2026-07 FND-01, ADR 0002)

## Context and Problem Statement

이 앱에는 인증이 없다. `docs/ARCHITECTURE.md` 가 "단일 사용자, 로컬 전용"을 명시적 전제로 둔다.
Express 는 기본적으로 `127.0.0.1` 에 바인딩한다(`HOST` 로 변경 가능).
`src/utils/csrfGuard.js` 가 상태 변경 요청(POST/PUT/DELETE/PATCH)에 대해 `Sec-Fetch-Site`(우선)
또는 `Origin`(폴백)으로 같은 오리진인지 검증하고, **둘 다 없으면 통과시킨다.**
스키마에는 사용자 개념이 전혀 없다 — `user_id` 컬럼이 한 곳도 없다.

서비스로 판매하려면 멀티유저와 인증이 필요하다. 그런데 독립 감사(2026-07)의 FND-01 은
CSRF 로 전체 거래내역을 원격 삭제할 수 있음을 실증했다.

인증 도입은 이 취약점 유형을 없애는 게 아니라 더 위험하게 만든다. 지금은 훔칠 자격증명이
아예 없어서 CSRF 의 피해가 "남의 브라우저를 빌려 내 데이터를 지우는 것"에 그치지만,
세션 쿠키가 생기면 브라우저가 자격증명을 자동으로 붙여주는 전형적인 CSRF 성립 조건이 갖춰진다.

## 결정 하나가 아니라 셋이다

인증 도입은 하나의 결정처럼 보이지만 실제로는 분리 가능한 세 결정이다.

1. **신원 출처(identity source)** — 누가 사용자인지 확인하는 방법. 자체 비밀번호 또는 OAuth IdP.
2. **세션 유지(session mechanism)** — 확인된 신원을 요청마다 어떻게 이어붙일지. 쿠키 세션 또는 JWT.
3. **데이터 격리(data scoping)** — 행이 누구 것인지 구분하는 방법.

셋 중 비용이 압도적으로 큰 건 3번인데, 3번의 비용은 1·2번을 무엇으로 정하든 똑같다.

| 항목 | 규모 |
|---|---|
| 사용자 데이터 테이블 | 11개 |
| 라우트 파일 | 18개 |
| `db.prepare` 호출 지점 | 133곳 |

테이블 11개는 두 종류로 나뉜다. 소유 루트 테이블 8개는 `payment_methods`, `categories`,
`transactions`, `installments`, `debts`, `app_settings`, `savings_products`, `recurring_rules`
이고, 부모를 통해 간접 소유되는 자식 테이블 3개는 `revolving_history`(→`payment_methods`),
`debt_interest_log`(→`debts`), `recurring_rule_months`(→`recurring_rules`) 다.

자식 테이블에도 `user_id` 를 중복해서 넣는다. 정규화 기준으로는 불필요하지만, 조인을 하나
빠뜨렸을 때 정규화된 스키마는 남의 데이터를 반환하고 비정규화된 스키마는 빈 결과를 반환한다.
실수의 방향이 다르다.

## Considered Options

### 옵션 1 — 서버 세션 + HttpOnly 쿠키 (SQLite 세션 테이블)

장점: 즉시 무효화가 가능하다(로그아웃, 비밀번호 변경, 기기별 강제 종료). `HttpOnly` 라
XSS 가 세션값을 읽지 못한다. 새 인프라가 필요 없다 — 이미 SQLite 를 쓴다. Express 가 SPA 를
같은 오리진에서 서빙하는 현재 구조와 그대로 맞는다.

단점: 서버 상태가 생긴다(만료 세션 정리가 필요하다). 다중 노드로 확장하면 세션 저장소를
공유해야 한다.

마이그레이션 비용: `users`·`sessions` 테이블 신설, 로그인/로그아웃 엔드포인트, 세션 해석
미들웨어. 데이터 격리 비용(133곳)은 별도이며 세 안 공통이다.

### 옵션 2 — JWT (Authorization 헤더)

장점: 서버 상태가 없다. 브라우저가 자동으로 붙이지 않으므로 CSRF 가 구조적으로 성립하지 않는다.
나중에 모바일 클라이언트나 서드파티 API 를 붙이기 쉽다.

단점이 기각 사유다. 토큰을 JS 가 읽을 수 있는 곳에 둬야 하므로 XSS 한 번이면 그대로 유출된다.
쿠키에 담으면 CSRF 가 다시 생겨서 무상태의 이점이 사라진다. 즉시 무효화하려면 결국 서버에
거부목록을 둬야 하는데, 그러면 무상태라는 유일한 장점이 없어진다. 재무 데이터를 다루는 앱에서
탈취 가능하고 즉시 무효화가 어려운 장기 자격증명은 나쁜 거래다.

마이그레이션 비용: 옵션 1 과 비슷하되 리프레시 토큰 회전 로직이 추가된다.

### 옵션 3 — OAuth 소셜 로그인 (Google 등)

장점: 비밀번호를 저장하지 않는다. 유출 책임 자체가 사라지고 비밀번호 재설정 흐름도 불필요하다.

단점: OAuth 는 옵션 1·2 의 대안이 아니다. 콜백이 끝난 뒤에도 요청마다 신원을 이어붙일 수단은
여전히 필요하므로, 실제로는 옵션 1 이나 2 위에 얹는 신원 출처일 뿐이다. 공개 콜백 URL 이
필요해 로컬 전용 모드와 양립하지 않고, 외부 IdP 도달성이 전제라 폐쇄망 배포에서는 로그인
자체가 불가능해진다.

마이그레이션 비용: 옵션 1 을 먼저 만든 뒤 그 위에 얹는 추가 작업이다.

### 하위 선택지 — 사용자별 DB 파일 분리 (기각)

`user_id` 컬럼 대신 사용자마다 SQLite 파일을 따로 두는 안도 검토했으나 기각한다.
마이그레이션을 사용자 수만큼 반복 실행해야 하고, `better-sqlite3` 는 동기 API 라 파일 핸들이
늘면 프로세스 자원 관리가 복잡해지며, 백업·복원 의미가 달라져 기존 export/import 기능을
전부 다시 설계해야 한다.

## Decision Outcome

**옵션 1 을 채택한다.** OAuth(옵션 3)는 나중에 신원 출처로 얹을 수 있게 열어두되 이번 범위에서
제외한다. JWT(옵션 2)는 채택하지 않는다.

세션 테이블 스키마는 다음과 같다.

    CREATE TABLE IF NOT EXISTS users (
      id INTEGER PRIMARY KEY,
      email TEXT UNIQUE,
      password_hash TEXT,
      created_at TEXT NOT NULL
    );

    CREATE TABLE IF NOT EXISTS sessions (
      id TEXT PRIMARY KEY,
      user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
      created_at TEXT NOT NULL,
      expires_at TEXT NOT NULL,
      last_seen_at TEXT NOT NULL
    );
    CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions(user_id);
    CREATE INDEX IF NOT EXISTS idx_sessions_expires ON sessions(expires_at);

세션 ID 는 CSPRNG(`crypto.randomBytes`)로 128비트 이상을 뽑아 base64url 로 인코딩한다.

쿠키 속성은 `HttpOnly`, `SameSite=Strict`, `Path=/` 이고 서비스 모드에서는 `Secure` 를 더한다.

`SameSite=Strict` 를 고른 이유는 이 앱에 외부 사이트에서 들어오는 진입 흐름이 없기 때문이다 —
공유 URL 도, 메일 링크도 없다. Lax 가 아니라 Strict 를 써도 잃는 게 없으므로, 잃는 게 없을 때는
더 좁은 쪽을 고른다. 비밀번호 재설정 메일처럼 외부에서 들어오는 링크가 생기면 그때 Lax 로 완화한다.

비밀번호 해싱은 `node:crypto` 의 `scrypt` 를 쓴다. 이 저장소는 보안 헤더조차 Helmet 없이 직접
구현했을 만큼 의존성 추가에 보수적이다(`src/utils/securityHeaders.js`). argon2id 가 이론적으로
낫지만 새 네이티브 의존성이 필요하고 그건 STOP&ASK 대상이다. scrypt 는 표준 라이브러리에 있고
이 용도에 충분하다.

## 두 모드 공존 설계

환경변수 `AUTH_MODE` 로 가른다. 기본값은 `single` 이다.

| 값 | 동작 |
|---|---|
| `single` (기본) | 로그인 없음. 지금과 완전히 동일하게 동작한다 |
| `multi` | 로그인 필수. 세션 쿠키로 사용자를 해석한다 |

이 설계의 핵심은 쿼리 경로를 두 벌 만들지 않는다는 것이다. 모드와 무관하게 모든 쿼리는
`req.userId` 로 스코프되고, 모드가 가르는 것은 `req.userId` 를 무엇으로 채우느냐 하나뿐이다.
`single` 은 상수 1, `multi` 는 세션 조회 결과다. 분기가 인증 계층 한 곳에만 있으면
"single 모드에서만 나는 데이터 유출" 같은 결함이 생길 자리가 없다.

`single` 모드에서도 마이그레이션으로 센티널 사용자(`id = 1`)를 만들고 기존 행 전부를
`user_id = 1` 로 채운다. 즉 `single` 모드는 "사용자가 없는 모드"가 아니라 "사용자가 언제나
1번인 모드"다.

`single` 모드에서 루프백 바인딩과 CSRF 가드는 지금 그대로 유지한다. 자격증명이 없는 상태의
통제는 달라질 이유가 없다.

## CSRF 방어 재설계 (FND-01 연관)

1. **`SameSite=Strict` 쿠키가 1차 방어가 된다.** FND-01 의 공격 벡터는 악성 페이지의 교차 사이트
   `<form>` POST 였는데, Strict 쿠키는 여기에 세션을 붙이지 않는다.
2. **기존 `csrfGuard` 는 2차 방어로 유지한다.** 쿠키 속성 하나에 전부를 걸지 않는다.
3. **폴백 규칙을 좁힌다.** 지금은 `Sec-Fetch-Site` 와 `Origin` 이 둘 다 없으면 통과시키는데,
   이건 자격증명이 없는 현재 상태에서만 안전하다. 바꿀 규칙은 이렇다 — 상태 변경 요청이 세션
   쿠키를 들고 있는데 브라우저 신호가 하나도 없으면 거부한다. 쿠키를 자동으로 붙이는 건
   브라우저인데 그 브라우저가 보내는 신호가 없다는 건 앞뒤가 맞지 않는다. 쿠키가 없는
   요청(curl, 서버 간 호출, 테스트 스위트)은 지금처럼 통과시킨다. 그쪽은 애초에 CSRF 가
   성립하지 않는다.
4. **GET 이 부작용을 갖지 않는다는 전제가 이제 하중을 받는다.** `SameSite=Strict` 여도 같은 사이트
   안에서는 GET 에 쿠키가 붙고, `csrfGuard` 는 GET 을 검사하지 않는다. 기존에는 관행이었던 것이
   이제 보안 요구사항이 된다.

로그인 엔드포인트 자체가 새 공격면이다. 무인증 앱에는 없던 것이라 지금은 어떤 속도 제한도 없다.
시도 횟수 제한과 실패 지연이 로그인과 함께 들어가야 한다.

## 마이그레이션 순서

각 단계는 독립적으로 배포 가능하다.

1. `users` 테이블과 센티널 사용자(id=1)를 만든다. `AUTH_MODE` 기본값은 `single` 이다.
   기존 사용자에게 아무 변화가 없다.
2. 11개 테이블에 `user_id` 를 추가하고(`NOT NULL DEFAULT 1`) 인덱스를 건다. 인증 미들웨어가
   `req.userId = 1` 을 주입하고 133곳의 쿼리를 스코프한다. 여전히 기존 사용자에게 변화가 없다.
3. `sessions` 테이블, 로그인/로그아웃, scrypt 해싱을 넣는다. `AUTH_MODE=multi` 를 옵트인으로 추가한다.
4. CSRF 폴백을 강화하고 로그인 속도 제한, `Secure` 쿠키, 서비스 모드 HTTPS 요구를 넣는다.
5. 선택적으로 OAuth 를 신원 출처로 추가한다.

1·2단계는 동작을 바꾸지 않으면서 가장 비싼 작업(133곳)을 끝낸다. 이 순서면 서비스 전환을 결국
하지 않기로 해도 2단계까지의 작업은 손해가 아니다. 스코프된 쿼리는 그 자체로 안전한 코드다.

## 이 ADR 이 결정하지 않는 것

- **저장 데이터 암호화** — multi 모드는 한 서버에 여러 사용자의 재무 데이터를 모은다. single
  모드에서는 파일이 사용자 본인 기기에 있었으므로 위협 모델이 다르다. SQLCipher 대 애플리케이션
  계층 필드 암호화는 별도 ADR 로 다룬다.
- **세션 만료 정책의 구체값** — 절대 만료와 유휴 만료 길이는 구현 시 정한다.
- **비밀번호 재설정 흐름** — 메일 발송 인프라가 필요하고, 그게 생기면 `SameSite` 를 Lax 로
  완화하는 트리거가 된다.
- **다중 노드 확장** — 현재 결정은 단일 프로세스를 전제한다.

## 재검토 트리거

| 트리거 | 재검토 대상 |
|---|---|
| 모바일 앱이나 서드파티 API 클라이언트가 생김 | 옵션 2(JWT) 재평가 |
| 다중 노드 배포가 필요해짐 | 세션 저장소를 공유 저장소로 이전 |
| 외부에서 들어오는 링크 흐름이 생김 | `SameSite=Strict` → `Lax` 완화 |
| 새 네이티브 의존성 추가가 승인됨 | scrypt → argon2id |
| 폐쇄망 배포 요구가 사라짐 | OAuth 를 기본 신원 출처로 승격 |
