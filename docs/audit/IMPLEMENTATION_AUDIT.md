## 검증 수단의 실제 방어력

테스트 통과 수는 방어력이 아니다. 2026-08-05 사이클에서 뮤테이션 테스트가
**"통과하는데 막지 못하는" 테스트를 다섯 번** 찾았다.

| 어디 | 통과하던 이유 |
|---|---|
| #425 소급 지문 | 6개 변형 중 4개 생존. `date`·`settlement`·`card_product_id` 변화를 못 봤다 |
| #425 2차 | 보강한 테스트도 **PUT 이 청구월을 같이 바꿔 줘서** 통과한 것이었다 |
| #428 재분류 지문 | 같은 함정. 청구월을 프리뷰 전에 고정하고서야 각 입력이 고립됐다 |
| #435 조건 문구 | 특정 문구의 **부재만** 봐서, 다른 말로 같은 뜻을 적으면 통과 |
| #437 실패 처리 | 에러 문구 부재만 봐서, 실패를 "카드가 없어요" 로 **잘못 말하는** 변형이 통과 |

`#435` 에서는 더 깊은 것이 나왔다 — **`<input type="number">` 는 `'null'` 같은 비숫자
값을 받으면 `.value` 가 `''` 로 읽혀 DOM 단언으로 결함이 안 보인다.** 실제 피해가 나는
지점(저장 요청 본문)까지 밀어야 잡힌다.

**판정: 단위 테스트만으로는 이 저장소의 결함 유형을 못 막는다.** 지문·문구·파생값
계열은 뮤테이션으로 확인해야 한다.

### 실거래 DB — 마이그레이션은 지연 적용이다 (2026-08-06 실측)

`data/finance.db` 는 마이그레이션 **008 까지 적용된 상태**이고 009~023 은 아직
안 돌았다. **결함이 아니라 구조다** — `src/db/init.js` 가 모듈 로드 시
`runMigrations(db)` 를 부르므로 **앱을 띄우는 순간 적용된다.** 2026-08-03 이후 앱을
안 띄웠을 뿐이다.

문제는 "15개가 한 번에 적용돼도 안전한가" 이고, 실거래 **사본**에서 전 과정을 돌려
확인했다(라이브 DB 는 읽기만 했다).

```
거래 건수      546 → 546              그대로
금액 합계      24,994,138 → 24,994,138  1원도 안 달라짐
기존 표 12개    전부 행수 동일
새 표 10개      전부 0건으로 생성
integrity_check ok
```

기존 행의 **값도 안 바뀐다.** 새 컬럼은 안전한 기본값만 받는다 —
`settlement='immediate'` 546건, `card_product_id`·`billing_month` 전부 NULL.
마이그레이션 021 의 주석이 약속한 그대로다. `016-payment-method-taxonomy` 가
결제수단을 재분류할 여지를 봤으나 10개 전부 이름·타입 그대로였다.

**판정: 안전하다.** 다만 적용 후 546건이 전부 `immediate` 라, 실제 신용카드 결제도
즉시 차감으로 잡힌다. 의도된 설계이고(자동 변환 금지 — ADR 0008), 그것을 사용자가
직접 바로잡으라고 M11 이 재분류 도구(#419)와 청구월 소급(#425)을 만들었다.
`accounts` · `card_products` 도 0건이라 M8·M11 기능은 **데이터를 넣는 것부터** 시작한다.

배포 시 이행 절차는 #371 이 다룬다.
