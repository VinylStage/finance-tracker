# PDCA 교차검토 — 2라운드 (개발팀 자체평가 vs 독립 감사 R2)

대상: 개발팀 자체평가([PR #187](https://github.com/VinylStage/finance-tracker/pull/187)) vs 독립 감사 2차([PR #204](https://github.com/VinylStage/finance-tracker/pull/204)). 두 세션은 서로의 결과를 모른 채 같은 코드(`78cf793`)에 같은 루브릭(`AUDIT_FRAMEWORK.md`)을 적용했다. 이 문서는 개발팀(=이 세션) 관점에서 두 결과의 불일치·감사가 지적한 패턴을 검토한다.

## 1. A1(접근통제) 판정 불일치 — 내 N/A는 과했다

- 내 자체평가: **N/A** — "다중 사용자 모델 자체가 없어 IDOR 위협모델이 성립하지 않는다"
- 독립 감사: **Partial**

**재검토 결과: 감사의 Partial이 더 타당하다고 판단한다.** 내 N/A는 A1을 "IDOR(사용자 간 데이터 접근 차단)"라는 좁은 사례로만 읽은 것이다. 하지만 `AUDIT_FRAMEWORK.md`의 근거 표준(OWASP Top10:2025 A01, CWE-862/639)이 실제로 다루는 범위는 "접근통제 일반"이지 IDOR 하나가 아니다. 이 렌즈로 다시 보면:

- 이 앱은 **어떤 요청이든 인증 없이 모든 API에 접근 가능**하다 — "단일 사용자"라는 건 설계 의도일 뿐, 그걸 강제하는 통제는 어디에도 없다.
- 이번 감사가 실증한 GET-CSRF 우회(§2)가 바로 그 증거다 — "정당한 사용자"와 "요청을 보낸 누군가"를 구분하는 장치가 CSRF 가드(메서드 기준 필터)뿐이고, 그 가드조차 전제(GET은 안전하다)가 깨지면 무력화된다.
- 즉 "다중 사용자가 없다"는 사실이 "접근통제가 불필요하다"를 함의하지 않는다 — 오히려 접근통제가 사실상 전무한 상태를 "위협모델 미해당"으로 단정한 게 내 판단의 오류였다.

**결론**: A1은 Partial로 정정한다. N/A는 "이 앱 특성상 이 축을 평가할 필요가 없다"는 뜻인데, 실제로는 "평가했더니 통제가 없다"는 걸 발견하고도 위협모델 자체를 좁게 잡아 회피한 셈이다. 다음 라운드부터는 각 항목 판정 전에 "이 항목의 근거 표준이 실제로 요구하는 범위가 뭔가"를 먼저 원문(OWASP/CWE 등)에서 다시 확인하는 절차를 넣는다.

## 2. 패턴 검토 — "시정 범위가 진단 범위보다 좁다"

감사가 예시로 든 FND-06/#142(리볼빙·부채 숫자 검증 — `debts.js`의 `/interest`만 패치, `POST /api/debts`의 `balance` 미검증 잔존)를 내 작업 기억으로 재구성하면:

**왜 이렇게 됐나**: FND-06 원 감사 findings는 "숫자 검증 없는 산술로 잔액이 오염될 수 있음"이라는 **증상**을 특정 재현 시나리오(이자 계산 흐름)로 제시했다. 나는 그 재현 시나리오를 정확히 재현하는 테스트를 작성하고, 그 테스트가 잡는 코드 경로(주로 이자 추가 엔드포인트)에 `asInt()` 검증을 넣었다. 뮤테이션 테스트(검증 제거 → 실패 재현 → 복구)도 정확히 그 경로에 대해서만 수행했다.

**놓친 지점**: "숫자 미검증 산술"이라는 **결함 유형**이 같은 라우트 파일 안에 몇 군데나 더 있는지 별도로 grep하지 않았다. `POST /api/debts`의 `balance` 필드도 사용자 입력을 그대로 산술(이자 계산)에 쓰는데, 이건 이자 추가 엔드포인트와 **동일한 결함 유형**이면서 원 재현 시나리오 밖에 있었다. 내 검증은 "이 테스트가 통과하는가"를 확인했지, "이 파일에 같은 클래스의 결함이 더 있는가"를 확인하지 않았다.

**일반화**: 감사 finding은 항상 구체적 재현 시나리오 하나로 온다 — 그게 자연스럽다. 문제는 내가 그 시나리오를 **결함 유형의 대표 사례**가 아니라 **수정 범위의 정의**로 취급했다는 것이다. Six Sigma Control 단계가 빠졌다는 감사의 지적과 정확히 같은 이야기다.

## 3. 패턴 검토 — "시정이 새 유형의 결함을 만든다"

세 건 전부 직접 코드를 다시 열어 감사 주장을 재확인했다(추측 아님).

### 3.1 #121 — GET이 부작용을 실행 (확인됨. 재현 상세 비공개 — [#205](https://github.com/VinylStage/finance-tracker/issues/205))

**왜 이렇게 됐나**: #121을 설계할 때 나는 "배치/스케줄러가 없는 앱이니 조회 시점 자가교정이 기존 `remaining_months` 동적계산 패턴과 일관된다"는 **아키텍처 일관성** 관점으로만 판단했다. 같은 세션 초반(M1)에 내가 직접 만든 `csrfGuard.js`의 "GET은 상태를 안 바꾼다"는 전제를 다시 열어보지 않았다 — 그 전제는 파일 안에 주석으로 명시돼 있었는데도, #121 작업 시점엔 그 파일을 아예 참조하지 않았다.

**놓친 지점**: "이 라우트가 관례적으로 잘 맞는가"와 "이 변경이 HTTP 메서드 시맨틱스(GET=안전)를 전제하는 다른 보안장치를 깨는가"를 별개 질문으로도 취급하지 않았다 — 애초에 후자를 질문 목록에 넣지 않았다.

### 3.2 #148 — 복잡도를 줄인 게 아니라 옮김 (확인됨: `resolveImportRow` 수동 카운트 CC 22, 감사 수치와 일치)

**왜 이렇게 됐나**: FND-14는 "복잡도 초과 함수 37개 중 상위 2개(data.js POST /import, cardImport.js)를 분리"였다. 나는 추출 **전** 함수의 CC가 떨어졌는지만 확인했다 — 정확히 떨어졌다(그게 추출의 정의니까). 추출**후** 새로 만든 `resolveImportRow` 자체의 CC를 감사가 쓴 것과 같은 방식으로 재계산하지 않았다.

**놓친 지점**: "원래 있던 문제가 해결됐는가"만 확인했지 "내가 새로 만든 코드가 같은 문제를 다시 갖고 있는가"를 확인하지 않았다. 리팩터링은 항상 코드를 어딘가로 옮기는 작업이라, 옮겨진 코드 자체가 새 감사 대상이라는 걸 놓쳤다.

### 3.3 #151 — 라벨은 있는데 조작이 안 됨 (확인됨: `Transactions.jsx:283`의 체크박스가 `className="hidden"` = `display:none`)

**왜 이렇게 됐나**: 이 체크박스는 실제로 #151 작업 중 직접 조사했다 — "`<label>`이 `<input>`을 감싸고 있으니 암묵적 라벨 연결이 성립하는가"를 DOM 레벨(`label[for]`/자식관계)까지 확인하고 "이미 접근 가능함"으로 결론 내렸다. **그 결론 자체는 라벨-이름 연결이라는 좁은 질문에는 맞다.**

**놓친 지점**: "접근 가능한 이름이 있는가"와 "키보드로 도달·조작 가능한가"는 다른 WCAG 기준(전자는 4.1.2, 후자는 2.1.1)인데 후자를 별도로 확인하지 않았다. 실제 브라우저 검증에서 스크린샷과 접근성 트리(`read_page`)는 확인했지만, **키보드만으로 Tab을 눌러가며 이 체크박스에 도달할 수 있는지는 한 번도 직접 눌러보지 않았다.** `display:none` 요소는 접근성 트리 조회 방식에 따라 라벨 연결은 보여도 tab 순서에서는 빠진다는 걸 그 시점엔 놓쳤다.

## 4. 재발방지 아이디어 (개발팀 관점)

감사가 권고한 "자동 게이트 이관"(Jidoka) 방향에 동의하되, 게이트가 못 잡는 부분에 대한 **작업 절차** 차원의 보완을 추가로 제안한다.

1. **변경 종류별 고정 체크리스트**(자동화 전 최소한의 수동 게이트):
   - HTTP 라우트 핸들러 변경 시: "이 핸들러의 메서드와 실제 부작용 여부가 여전히 일치하는가?" (GET=읽기전용 불변식 재확인)
   - 리팩터링/함수 추출 시: "추출된 새 함수의 복잡도를 원래 함수와 같은 기준으로 다시 측정했는가?"
   - 접근성 라벨링 시: "이름 연결"과 별개로 "키보드 Tab만으로 실제 도달·조작 가능한가?"를 직접 눌러 확인했는가?
2. **결함 유형 단위로 grep 후 수정 범위 확정**: finding의 재현 시나리오를 고친 뒤, 같은 파일(최소) 또는 같은 라우트 그룹(이상적)에서 동일 패턴을 검색해 남은 인스턴스가 없는지 확인하고 나서 "완료"로 표시한다.
3. **보안장치가 의존하는 불변식을 문서화하고 grep 가능하게 만들기**: `csrfGuard.js`의 "GET은 안전하다" 같은 전제는 주석에만 있으면 다음 변경에서 다시 깨질 수 있다. 이런 불변식은 `docs/ARCHITECTURE.md`의 "지켜야 할 불변식" 섹션 같은 곳에 모아두고, 관련 라우트 파일을 고칠 때 그 문서를 먼저 확인하는 습관을 명시적 절차로 만든다.
4. **자체평가와 독립감사가 갈리는 항목은 근거 표준 원문을 재확인**: A1처럼 판정이 갈렸을 때, "내 판단이 맞다"고 방어하기 전에 근거 표준(OWASP/CWE 등)이 실제로 정의하는 범위를 다시 읽는다 — 이번에 그렇게 해서 내 판정을 정정했다.

## 5. 종합

- A1: 내 판정(N/A) → **Partial로 정정**
- GET-CSRF(#121): 감사 발견 인정, 백로그 이슈화([#205](https://github.com/VinylStage/finance-tracker/issues/205)) — 사용자 판단으로 즉시 수정은 보류(로컬 전용 사용, 우선순위 낮음). 미시정이므로 재현 상세는 비공개 저장소에서 관리
- FND-06 부분시정, #148 복잡도 이동, #151 키보드 조작성: 전부 직접 재확인해 감사 주장이 정확함을 확인
- 다음 라운드 실행 시(사용자 지시 대기 중) 위 4가지 재발방지 아이디어를 실제 작업 절차에 반영 제안
