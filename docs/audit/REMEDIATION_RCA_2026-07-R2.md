## 0. 이 문서의 위치

2차 독립 감사 보고서([`AUDIT_REPORT_2026-07-R2.md`](./AUDIT_REPORT_2026-07-R2.md)) §6.2가 리메디에이션에서 두 가지 패턴을 지목했다.

1. 시정 범위가 진단 범위보다 좁다
2. 시정이 새로운 유형의 결함을 만들었다

본 문서는 그 지목을 **가설로 두고 M0~M5 이력 전체를 다시 훑어 검증**한 결과다. 몇 번, 어떤 조건에서 반복됐는지 세고, 왜 반복되는지 메커니즘을 특정하고, 재발 방지책을 실제로 구현해 실효성을 확인했다.

후반부(§5)는 개발팀 자체평가(PR #187)와 독립 감사(PR #204)의 교차검토다. 판정이 갈린 11개 항목, 특히 **A1(N/A vs Partial)** 을 정면으로 다룬다.

**중요**: §5의 교차검토는 양측 판정이 **모두 확정·커밋된 이후**에 수행했다. 2차 감사(PR #204)는 PR #187의 내용을 보지 않은 상태에서 작성됐다.

## 1. 요약

가설은 **양쪽 다 사실로 확인됐다.** 다만 원인의 소재가 감사팀의 최초 진단과 달랐다 — 이 부분은 자기정정으로 §1.2에 별도로 적었다.

### 1.1 핵심 수치

FND-06(숫자 필드 미검증)을 대상으로, 결함 유형 전체를 기계적으로 세어봤다.

| 시점 | 미검증 숫자 필드 | 해당 핸들러 |
|---|---:|---:|
| 리메디에이션 **전** (`4c40ccf`) | **22건** | 9개 |
| 리메디에이션 **후** (`78cf793`) | **16건** | 8개 |
| 실제 시정된 것 | **6건** | — |

**결함 유형의 73%가 살아남았다.** 시정된 6건은 1차 감사 보고서가 본문에 인용한 위치와 정확히 일치한다(revolving 5개 필드 + debts `interest_amount` 1개).

측정에 쓴 검사기는 **50줄, 신규 의존성 0개**다(§4.1). 진단 시점에 이걸 돌렸다면 22건이 전부 목록에 올랐을 것이다.

### 1.2 감사팀 자기정정 — 원인의 소재

2차 감사 보고서 §6.2는 이 패턴의 원인을 "**시정 완료 판정 기준이 증상 소멸이었다**"고 서술했다. 개발팀 쪽에 무게를 실은 서술이다. 이력을 다시 훑은 결과 **그 서술은 부정확하다.**

1차 감사 FND-06의 **위치** 항목은 다음과 같다.

> **위치**: `src/routes/revolving.js:39`, `src/routes/revolving.js:59`, `src/routes/debts.js:78`

`debts.js:78`은 `POST /:id/interest`이고, `POST /api/debts`(`debts.js:24`)는 **1차 감사가 아예 보지 않았다.** 이슈 #142의 완료 기준은 이 위치 목록의 충실한 전사이고, 개발팀은 그 완료 기준을 정확히 이행했다.

즉 **시정은 진단에 충실했고, 진단이 불완전했다.** 근본원인은 개발팀의 완료 판정이 아니라 **감사·시정 양쪽 모두 "결함 유형 전수조사"라는 단계를 갖고 있지 않다**는 공정상의 공백이다. 이 정정을 §3의 분석 전제로 삼는다.

### 2.2 패턴 B — 시정이 새 결함/새 제약을 생성

#### B-1. #121 — 할부 자동완료 → 부작용 있는 GET

이슈 #121의 완료 기준 첫 줄:

> `- [ ] 자동 종료 처리 방식 결정 (읽기 시점에 갱신 vs 별도 배치/트리거)`

**"읽기 시점에 갱신"이 선택지로 명시돼 있고, 그것이 채택됐다.** 그 결과 안전 메서드 경로가 쓰기를 수행하게 됐고, `csrfGuard`가 상태변경 **메서드**만 검사하므로 이 쓰기 경로는 무검증이다(R2 §4.2). 미시정 상태라 재현 상세는 비공개로 관리한다([#205](https://github.com/VinylStage/finance-tracker/issues/205)).

가장 주목할 점은 회귀 테스트다. `4f5cf46`이 추가한 테스트는 이렇다.

```js
test('#121: 청구 기간이 끝난 진행중 할부는 GET 시점에 자동으로 완료 처리됨', ...)
  assert.strictEqual(updated.status, '완료', ...)
```

**테스트가 결함을 명세로 고정했다.** 이 테스트가 있는 한 R2 §4.2의 수정은 테스트 실패를 유발한다 — 즉 회귀 테스트가 시정을 막는 방향으로 작동한다.

> 이슈 단계에서 "읽기 시점 갱신"을 선택할 때 **보안 영향 검토가 완료 기준에 없었다.** 대안("저장하지 않고 조회 시점에 계산")은 같은 목적을 달성하면서 이 문제를 만들지 않았고, 실제로 같은 라우트가 파생 값 일부를 이미 그 방식으로 처리하고 있다.

## 3. 근본원인 분석

### 3.1 RC-1 — 완료 기준이 "진단이 인용한 위치"의 전사(轉寫)다

감사 보고서의 **위치** 항목은 결함 유형을 설명하기 위한 **표본**인데, 이슈 전환 과정에서 **작업 지시서(work order)** 로 성격이 바뀐다.

증거: #142 완료 기준 4항목 ↔ FND-06 인용 위치 4곳의 1:1 대응. #148 완료 기준 2항목 ↔ FND-14 표의 상위 2행.

여기에 감사 쪽의 대칭적 공백이 겹친다 — **감사도 전수조사를 하지 않는다.** FND-08은 `EXPLAIN`을 2개 쿼리에만 돌렸고, FND-06은 `grep` 없이 눈으로 읽은 3곳을 적었다. 진단이 표본이니 시정도 표본이 된다.

### 3.2 RC-2 — 근본 시정조치가 완료 기준 **밖**에 서술된다

이것이 가장 구조적인 원인이다. 이슈 #142 본문에는 정답이 이미 적혀 있다.

> **수정 방향**
> - `revolving.js`(POST/PUT), `debts.js`(interest 처리)에 기존 `asInt()` 적용
> - `data.js` 임포트 경로에도 날짜/금액 타입 검증 추가
> - **근본원인: 금액 필드 검증을 공통 스키마로 정의해 "유틸이 있는데 안 쓰는" 상태를 구조적으로 차단**
>
> **완료 기준**
> - [ ] revolving.js POST/PUT에 asInt 적용
> - [ ] debts.js interest 처리에 asInt 적용
> - [ ] data.js 임포트 검증 추가
> - [ ] 문자열 숫자 입력 시 400 또는 정상 강제변환 확인 테스트

**세 번째 불릿(근본 시정조치)이 완료 기준 체크리스트에 없다.** 1차 감사 §6.1도 좌열(즉시수정)/우열(근본 시정조치)을 나눠 제시했는데, 이슈로 변환될 때 **좌열만 체크박스가 됐다.**

ISO 9001 조항 10.2가 correction과 corrective action을 구분하라고 요구하고, 프레임워크 Part 3 운영규칙 2가 이를 그대로 옮겨 적었다. **문서에는 있지만 워크플로에는 없다.** 이슈는 체크리스트가 다 채워지면 닫히고, 근본 시정조치는 아무 곳에도 승계되지 않는다.

### 3.3 RC-3 — 회귀 테스트가 결함 유형이 아니라 **감사 PoC**를 전사한다

먼저 사실관계를 정확히 해둔다. **테스트 부재는 원인이 아니다** — 리메디에이션 커밋 23건 중 **19건이 테스트 파일을 동반**했다. 테스트 규율 자체는 양호하다.

문제는 테스트의 *범위*다. #142가 추가한 테스트 이름이 그대로 말해준다.

```
test('FND-06: 감사 PoC — debts 이자 추가에 문자열 interest_amount를 보내면 400')
```

**"감사 PoC"** 가 테스트 이름에 들어있다. 테스트는 감사의 재현 절차를 옮겨 적은 것이고, 따라서 **PoC의 범위를 그대로 상속한다.** `POST /api/debts`에 대한 테스트는 애초에 존재할 이유가 없었다 — PoC가 거기를 치지 않았으니까.

가장 극단적인 형태가 B-1이다. #121의 회귀 테스트는 결함(GET이 쓰기를 함)을 **명세로 고정**해서, 이제 그 테스트가 시정을 방어한다.

### 3.4 RC-4 — 지표가 대리변수일 때 대리변수만 달성된다

#151의 지표는 "라벨 연결 개수"였다. 라벨은 접근성의 **대리변수**이고 실제 요구는 "보조기술·키보드로 조작 가능한가"다. `display:none` 체크박스는 대리변수를 만족시키면서 본래 요구를 위반한다.

#148도 같은 구조다. "동작 동일성"은 리팩터링 안전성의 대리변수이지 **복잡도 감소의 지표가 아니다.** 그래서 CC가 안 내려가도 통과한다.

이 패턴은 굿하트 법칙(측정이 목표가 되면 좋은 측정이 아니게 된다)의 교과서적 사례다.

### 3.5 RC-5 — 검증(verification)이 **변경 자체**를 대상으로 삼지 않는다

ISO/IEC 12207의 검증은 산출물뿐 아니라 변경도 대상으로 한다. 그런데 M0~M5의 완료 기준은 예외 없이 **"요구된 것이 달성됐는가"** 만 묻고 **"이 변경이 기존 방어 모델·품질 지표를 훼손하지 않았는가"** 는 묻지 않는다.

- #121: "자동 완료 처리가 되는가" ✅ / "CSRF 방어 모델과 충돌하는가" ❌ 미검토
- #148: "동작이 같은가" ✅ / "CC가 실제로 내려갔는가" ❌ 미측정
- #151: "라벨이 붙었는가" ✅ / "조작 가능한가" ❌ 미검토

1차 PDCA 교차검토(§A4)도 이 근처에 도달해 있었다 — "정량 임계값이 있는 항목은 '완전 해소'의 기준 자체가 모호해 잔여 갭이 생기기 쉽다"는 관찰이다. 본 분석은 그 관찰의 **메커니즘**을 RC-2/RC-4로 특정했다.

## 4. 재발 방지 방안

우선순위 순으로 4개를 제안한다. **1·2번은 실제로 구현해 실효성을 확인했다.**

### 4.1 [최우선] 결함 유형 전수조사를 진단·시정 양쪽의 필수 산출물로 만든다

**규칙**

- 감사 보고서의 **위치** 항목에 `(표본)` 또는 `(전수)` 를 명시한다. 표본이면 시정 이슈가 전수조사를 수행한다.
- 이슈 템플릿의 완료 기준에 고정 항목 2개를 추가한다.
  - `[ ] 결함 유형 정의: <한 문장>`
  - `[ ] 전수조사 근거 첨부 — 실행한 명령과 그 출력(발생 위치 전체 목록)`
- 시정 후 같은 명령을 재실행해 **0건 또는 잔여 목록**을 PR 본문에 남긴다.

**실효성 검증 (실제 구현·실행함)**

AST 기반 검사기 약 50줄, **신규 의존성 0개**(파서는 `lighthouse`가 이미 끌고 오는 `meriyah`). FND-06 유형("`req.body`의 숫자 필드가 `asInt`/`asNumber`를 거치지 않음")을 검사한다.

### 4.2 [최우선] 자동 게이트로 이관 — 사람이 매번 확인할 항목을 줄인다

프레임워크 Part 3 운영규칙 3(TPS Jidoka)의 직접 적용이다. 위 검사기를 CI 게이트로 편입하고, 같은 방식으로 **HTTP 안전 메서드 계약**도 검사한다.

**게이트 A — GET 핸들러에서 DB 쓰기 금지**

`router.get(...)` 핸들러와 그 핸들러가 호출하는 헬퍼까지 따라가 `db.prepare()` 인자에 `INSERT/UPDATE/DELETE`가 있으면 실패시킨다. 현재 코드에 실행한 결과:

```
✗ <라우트 1건>  GET /
    <파일:라인>  UPDATE … (상세 비공개 — #205)
→ 위반 1건
```

**#121이 도입한 결함(R2 §4.2)을 정확히 잡는다.** 이 게이트가 있었다면 PR #183이 CI에서 빨간불이 났을 것이다.

**게이트 B — §4.1의 숫자 필드 검사기**

임계값을 현재 16건으로 고정(baseline)하고 **증가하면 실패**시킨다. 그러면 신규 라우트가 같은 결함을 갖고 들어올 수 없고, 잔존 16건은 별도 이슈로 점진 해소한다.

> **경고 — 게이트는 반드시 "빨간불이 켜지는지" 먼저 확인해야 한다.**
> 이 게이트 A를 처음 작성했을 때 `UPDATE\s+\w` 뒤에 `\b`를 붙인 탓에 테이블명이 두 글자 이상이면 매치되지 않아, **위반이 있는데 "위반 없음"을 출력했다.** 알려진 결함(#121)을 대상으로 검증했기에 발견했다.
> 이 저장소는 이미 같은 유형의 사고를 겪었다 — FND-16 / `c644282` "CI 문법검사 게이트가 실패를 감지하지 못하는 문제". **게이트 추가 시 의도적으로 실패시켜 확인하는 절차를 필수 단계로 둘 것**을 다시 권고한다(1차 감사 §6.1이 이미 권고한 항목).

### 4.3 근본 시정조치를 별도 이슈로 강제 분리한다 (correction ≠ corrective action)

**규칙**

- 감사 보고서 §6.1 우열(근본 시정조치)에 항목이 있으면 **반드시 별도 이슈**를 만든다. 즉시수정 이슈 본문에 `Refs:`로 연결한다.
- 즉시수정 이슈는 체크리스트 충족 시 닫아도 되지만, **근본 시정조치 이슈는 마일스톤 종료 조건에 포함**한다.
- 이슈 템플릿의 "수정 방향" 산문에 근본원인을 적는 것만으로는 완료 추적이 되지 않는다 — 체크박스가 아니면 워크플로에 존재하지 않는 것으로 취급한다.

#142가 이 규칙을 따랐다면 "금액 필드 검증 공통 스키마 정의" 이슈가 지금도 열려 있었을 것이고, R2 §4.3·§4.7은 그 이슈의 범위 안에 들어왔을 것이다.

### 5.2 쟁점 — A1: N/A(개발팀) vs Partial(감사)

**개발팀 근거**: "다중 사용자 모델 자체가 없는 단일사용자 로컬 앱 — 이 항목이 원래 전제하는 위협모델(타 사용자 데이터 접근)이 성립하지 않음"

**감사 근거**: R2 §3.1 — ① 무인증 전제를 강제하는 게이트 부재 ② 부작용 GET의 CSRF 우회 ③ 파괴적 라우트의 확인 토큰 부재

#### 절차적 논점

프레임워크 Part 2는 판정 척도를 **Pass / Partial / Fail 세 가지로만** 정의한다(ISO 9001 10.2 부적합 판정 구조). **N/A는 척도에 없다.** 새 척도 값을 도입하려면 프레임워크 개정이 선행돼야 하고, 그 전까지는 사이클 간 비교(Part 3 운영규칙 5의 "Pass 비율 추이")가 성립하지 않는다 — 분모가 달라진다.

실제로 #187의 종합표는 21항목을 Pass 13 / Fail 3 / 미측정 1 / N/A 2 / 보류 1로 쪼갰고, **Pass 비율을 산출하지 않았다.** 1차 감사가 남긴 기준선(Pass 19.0%)과 이어지지 않는다.

#### 실질적 논점 — 부분적으로 개발팀이 옳다

개발팀 주장은 **A1의 "IDOR" 부분에 대해서는 정확하다.** 소유자 없는 데이터에 소유자 검증을 요구하는 것은 무의미하고, 감사가 이를 Fail로 몰았다면 그건 잘못이었을 것이다. 감사도 Fail이 아닌 Partial로 판정한 이유가 그것이다.

그러나 N/A는 **"이 항목에 대해 볼 것이 없다"** 를 뜻하고, 감사가 실측한 세 가지는 그 결론을 지지하지 않는다.

- ②는 **실제로 재현됐다** — 안전 메서드 경로로 DB 상태가 바뀐다. 위협모델과 무관하게 존재하는 접근통제 결함이다(재현 절차 비공개, [#205](https://github.com/VinylStage/finance-tracker/issues/205)).
- ③도 **실제로 재현됐다** — 확인 토큰 없이 전체 거래가 삭제된다. 같은 코드베이스의 다른 파괴적 라우트 2곳은 토큰을 요구하므로, 이건 설계 전제가 아니라 **정책 불일치**다.
- ①은 판단 문제지만, 문서로만 존재하는 전제와 코드로 강제되는 전제는 감사에서 같은 무게를 갖지 않는다.

**감사팀 입장**: A1은 Partial을 유지한다. 다만 판정 사유를 명확히 분리해 기록한다 — **"IDOR 부분은 해당 없음, 접근통제 축의 나머지(부작용 GET·확인 토큰 정책)에서 실측 결함 2건."** 이렇게 쓰면 개발팀 주장의 타당한 부분과 감사의 실측이 둘 다 보존된다.

#### 이 쟁점은 1차 감사가 이미 예고했다

1차 감사 보고서 §6.2 루브릭 개선 제안 4번:

> **A1/A4/A6의 "단일 사용자 예외" 처리 기준을 명문화할 것을 권고한다.** 현재 세 항목 모두 "설계상 해당 없음"과 "기준 미충족"의 경계가 감사자 재량에 맡겨져 있어 **사이클 간 판정 일관성을 해친다.**

**정확히 예고된 대로 발생했다.** A1·A4·A6ㅡ세 항목 전부에서 판정이 갈렸다. 이는 어느 쪽의 판단 오류가 아니라 **루브릭의 미비**다.

**공동 권고 (프레임워크 개정 제안)**: Part 2에 다음을 명문화한다.

1. 척도는 Pass/Partial/Fail 셋으로 유지하고 **N/A는 쓰지 않는다.** 위협모델 미해당은 **"Pass(위협모델 미해당) + 사유"** 로 기록하되, **그 판단이 강제되는지(코드 게이트) 여부를 근거란에 반드시 적는다.** 강제되지 않으면 Partial.
2. A1을 **"접근통제(IDOR + CSRF + 파괴적 동작 확인)"** 로 확장한다. (1차 감사 §6.2 제안 3번과 동일 — 미반영 상태)
3. A6의 통과기준을 명확히 한다 — Part 2 본문은 "HTTPS 강제 / `.env` 미커밋 / 로그 내 평문 크레덴셜 0건" 3개인데, Part 1 ISO 25010 표에는 "SQLite 파일 암호화"가 별도로 있다. §5.3의 판정 차이가 여기서 발생했다.

### 5.3 A6 — Fail(개발팀) vs Partial(감사): 루브릭 자체가 모호하다

양측 **사실 인식은 완전히 같다** — `data/finance.db`는 평문, `.env`는 미커밋, HTTPS 없음.

차이는 채점 대상이다.

- 개발팀: Part 1 ISO 25010 표의 "SQLite 파일 암호화"를 기준으로 → 미충족 → **Fail**
- 감사: Part 2 A6의 통과기준 3개("HTTPS 강제 / `.env` 미커밋 / 로그 내 평문 크레덴셜 0건") 중 2개 충족 → **Partial**

**Part 2 통과기준에 DB 암호화가 없다.** 어느 쪽도 오독이 아니고, 루브릭이 두 층위에서 다른 것을 요구하고 있다. §5.2의 공동 권고 3번으로 해소해야 한다.

개발팀이 `file` 명령으로 직접 확인한 것은 좋은 실증이고, A6를 신규 이슈 후보로 올린 판단도 타당하다. 다만 이 앱의 위협모델(로컬 단일 사용자, 디스크 접근 = OS 계정 탈취)에서 DB 암호화의 실효는 **키를 어디에 두느냐**에 전적으로 달려 있다 — 같은 디스크에 키를 두면 방어력이 거의 없다. 이슈화 시 이 점을 먼저 정리할 것을 권고한다.

### 5.4 감사 판정이 실측으로 지지되는 항목 (B1·B2·B5·B6·C6)

| # | 개발팀 판정·근거 | 감사가 추가로 확인한 것 |
|---|---|---|
| **B1** Pass(근사) | "전체 81.38%(c8 실측)" | 숫자는 맞다. 다만 그 81.38%는 **백엔드 전용**이다. `client/` 4,003 LOC(코드베이스의 53%)는 테스트 파일 0건·러너 설정 0건으로 **지표에 아예 안 잡힌다.** 전체 기준 실질 ≈44% |
| **B2** 미측정 | "jscpd 등 신규 devDependency 필요(사전 승인 대상)" | **신규 의존성 없이 측정 가능했다.** 60줄 클론 검출기로 실측: 전체 **1.97%**(백엔드 1.12% / 프론트 2.58%) → **Pass**. 전후 비교도 가능: 3.02% → 1.97%. 도구 도입이 막혀 있다는 전제가 실제 제약이 아니었다 |
| **B5** Pass | "`utils`·`db`·`services` 어디도 `routes`를 require하지 않음 — 단방향 확인" | 의존 **방향**은 감사도 동일하게 확인(순환 0건, 역방향 0건). 그러나 B5의 통과기준은 "**라우트-컨트롤러-모델 분리** + 순환의존 0건" 두 가지다. 라우트 15개가 `db/init`을 직접 require하고 인라인 `db.prepare()`가 **124개** — 모델 계층이 없다. 기준의 절반만 충족 |
| **B6** Pass | "`db.transaction()` 사용, 전역 에러 미들웨어 + ErrorBoundary 존재" | **메커니즘의 존재**는 감사도 확인. 그러나 **동작**을 HTTP로 검증하면 결함 6종: 없는 리소스 PUT/DELETE 7개 라우트가 200(404 아님), 입력 오류 6종이 500(400/409 아님), 임포트 카테고리 생성이 트랜잭션 밖 |
| **C6** Pass | "FND-07(N+1 제거)·FND-08(sargable 인덱스) 완료" | **인용된 두 항목이 완료된 것은 사실이고 감사도 `EXPLAIN`으로 재확인했다.** 그러나 그것이 C6 통과기준("주요 조회 인덱스 존재")의 충족을 뜻하지 않는다 — `approval_number` 인덱스가 없어 카드 임포트 중복체크가 **행당 풀스캔**이다(200k건/500행 **2,097.9ms** → 인덱스 추가 시 1.3ms) |

**C6는 이 교차검토에서 가장 중요한 항목이다.** 개발팀의 C6 Pass 근거는 "직전 감사가 지적한 항목이 처리됐다"이고, 이는 **§3의 RC-1(진단 범위 = 시정 범위)이 감사 단계에서 반복된 형태**다. 자체평가가 직전 감사의 findings 목록을 체크리스트로 삼으면, 그 목록 밖의 결함은 구조적으로 보이지 않는다.

### 5.5 B3 — 개발팀의 Fail 근거에 사실오인이 있다

#187의 B3 근거:

> "1라운드는 **완화된 기준(CC≤25)** 으로 37건 중 2건만 처리. 프레임워크 원 기준(≤10)으로 재면 **위반 건수는 훨씬 많을 것**"

두 가지를 정정한다.

**① 1차 감사의 임계값은 25가 아니라 10이었다.** 1차 보고서 B3 판정란 원문: `함수당 Cyclomatic ≤ 10 | 218개 중 37개(17.0%) 초과, 최대 43 | Fail`. FND-14 본문도 "SonarQube Cognitive 임계값 15와 **Cyclomatic 상한 10**을 크게 초과"라고 적었다. 완화된 기준은 적용된 적이 없다. (1차 PDCA 교차검토 §B2도 "CC 25 획일적 임계값"이라고 적어 같은 오인을 공유하고 있다 — 그 문단의 전제도 정정이 필요하다.)

**② "훨씬 많을 것"이라는 예측은 실측과 반대다.** AST 기반 McCabe로 실측한 결과 **237개 중 8개(3.4%)**, 최대 CC 22다. → 감사 판정 **Partial**.

**③ 1차 감사의 "37개(17.0%), 최대 43"은 재현되지 않는다.** 같은 도구로 `4c40ccf`를 측정하면 백엔드 **205개 중 7개(3.4%)**, 최대 23이다. 최대치로 지목된 `data.js:53 POST /import`는 표준 McCabe(중첩 함수 분리 집계)로 **CC 9**, 중첩 포함 집계로도 **CC 31**이며 어느 쪽도 43이 아니다.

1차 감사는 측정 방법을 "결정점 계수 + 1의 **근사치**"라고 밝히고 "프론트엔드 수치는 과대평가 경향(정확도 중간)"이라는 단서를 달았으나, **"백엔드 수치는 신뢰도가 높다"는 부분은 성립하지 않는다.** 218개라는 함수 수가 백엔드 단독 205개와 거의 같은 것으로 보아, 라인 스캔 방식이 함수 경계를 잘못 잡아 인접·상위 스코프의 결정점을 합산했을 가능성이 높다.

**이 정정의 파급**

- 이슈 #148은 **부풀려진 문제 진술**(37개, 최대 43) 위에서 생성됐다.
- 1차 PDCA §B2의 반론("CC 25 임계값이 단일 개발자 프로젝트에 과하다")은 **틀린 숫자를 상대로 한 논쟁**이었다. 실제 백엔드 위반은 처음부터 7개였다.
- 다만 §2.2 B-2의 결론(**리팩터링이 클래스 지표를 바꾸지 못했다**)은 전후 동일 도구 측정으로 그대로 유효하다: 3.4% → 3.4%, 최대 23 → 22.
- "37개 중 35개가 남았다"(1차 PDCA §A1)는 서술도 과장이다 — 그 37 중 대부분은 JSX 조건부 렌더(`&&`)를 결정점으로 센 프론트엔드 수치로 보인다.

**교훈**: 정량 지표를 근사 도구로 측정해 Fail 판정과 이슈 생성의 근거로 쓸 때는, 최소한 **최대치 1건을 수작업으로 검산**해야 한다. 본 감사는 `resolveImportRow`의 CC 22를 결정점 21개까지 손으로 세어 확인했다.

### 5.6 B4 — 개발팀 근거가 더 구체적이다 (부분적으로 개발팀 지지)

#187이 제시한 근거는 감사가 갖지 못한 정보다.

> "PR 작성자와 GitHub 계정이 동일해 리뷰어 지정이 API 레벨에서 거부됨(`422 Review cannot be requested from pull request author`)"

이것은 "리뷰어가 없다"가 아니라 **"구조적으로 불가능하다"** 를 입증한다. 감사는 `CODEOWNERS`가 단독이라는 정황만 확인했다.

다만 판정은 **Partial이 더 정확하다** — B4의 통과기준은 "PR 크기 중앙값 <400줄, 응답 1영업일 이내"이고, PR churn 중앙값은 **87줄**로 충족한다. 독립성 문제는 실재하지만 **B4의 통과기준이 측정하는 대상이 아니다**(ISO 9001 9.2 항목이지 Google/MS 리뷰 관행 항목이 아니다).

**공동 권고**: 이 구조적 제약은 사람으로 해소할 수 없으므로 **자동 게이트로 대체한다**(§4.2). 리뷰어 부재의 실질적 위험은 "다른 눈이 놓친 것을 잡지 못한다"인데, 그 역할의 상당 부분은 정적 게이트가 대신할 수 있다. 감사 보고서 §5 권고 B3-1/B1-2와 동일한 방향이다.

### 5.7 C4/C5 — 판정은 같지만 측정 조건이 다르다 (중요)

양측 모두 Pass다. 그러나 근거가 다르다.

| | 개발팀 #187 | 감사 #204 |
|---|---|---|
| 데이터 규모 | 명시 없음(기본 시드 DB로 추정) | **20,000건 / 200,000건** 명시 |
| 샘플 | 20회 | 30회 (워밍업 3회 별도) |
| 대상 | 4개 엔드포인트 | 22개 엔드포인트 |
| 결과 | `/api/categories` p95 **1.4ms**, dashboard p95 **3.7ms** | 20k에서 dashboard p95 **7.6ms**, 200k에서 **145.9ms**; export 200k p95 **327.5ms** |

**데이터 규모를 명시하지 않은 성능 측정은 스케일링 결함을 구조적으로 볼 수 없다.** 그리고 실제로 그렇게 됐다 — 개발팀 측정에서 카드 임포트 중복체크(§5.4 C6)는 데이터가 적어 드러나지 않는다. 이 쿼리의 비용은 `O(임포트 행 수 × 전체 거래 수)`라서, 기본 시드 DB에서는 사실상 0ms다.

**공동 권고**: 성능 측정 결과에 **데이터 규모를 필수 기재 항목**으로 넣고, 최소 2개 규모(현실적 규모 / 10배)에서 측정한다. `PERFORMANCE_BASELINE.md`가 이미 재측정 트리거로 "거래 데이터가 크게 늘어나면"을 적어뒀는데, 그 트리거를 기다리지 말고 처음부터 두 규모로 재는 편이 싸다.

### 5.8 개발팀 자체평가에서 감사가 수용하는 점

교차검토는 양방향이어야 하므로 명시한다.

1. **A6의 DB 평문 저장을 `file` 명령으로 직접 실증**했다. 감사는 코드/gitignore 확인에 그쳤다.
2. **B4의 `422` API 응답**은 구조적 제약의 결정적 증거다. 감사보다 근거가 강하다.
3. **B3/B4를 "기지 사항"으로 분류하고 중복 이슈 생성을 생략**한 판단은 옳다. 1차 PDCA에서 이미 다룬 항목을 다시 이슈화하면 백로그만 부풀린다.
4. **C7을 "판정 보류(리렌더링 프로파일링 미실시)"로 정직하게 남긴 것**은 좋은 태도다. 감사는 C7을 Pass로 판정했지만 같은 미확인 사항을 §3.3에 명시했다 — 실질적으로 같은 인식이다.
5. **A5의 CORS 판단**("동일-origin 구조라 불필요")은 감사와 동일하며 정확하다.

## 6. 2차 감사 보고서 자체 정정

교차검토 과정에서 [`AUDIT_REPORT_2026-07-R2.md`](./AUDIT_REPORT_2026-07-R2.md)의 오류 2건을 확인했다. 해당 보고서 §6.3에 정정을 반영했다.

### 6.1 [정정] "1차 감사에 비교 가능한 기준선이 없다"는 서술은 사실과 다르다

R2 §6.3은 "1차 감사는 루브릭 21항목에 대한 Pass/Partial/Fail 집계를 동일한 형식으로 제시하지 않아 직접 비교 가능한 기준선이 없다"고 적었다. **틀렸다.** 1차 보고서 §6.2에 추적 지표 표가 있다.

| 지표 | 사이클 1 | 사이클 2 (R2) |
|---|---:|---:|
| **Pass 비율** | **19.0% (4/21)** | **52.4% (11/21)** |
| **Fail 항목 수** | **7** | **0** |
| Critical/High 결함 수 | 5 | 0 (신규 High 2건은 §4.1·§4.2) |
| 코드 중복률 | 8.48% (방법 미상) | 1.97% (Type-1 클론) |
| CC>10 함수 비율 | 17.0% (근사, 재현 안 됨) | 3.4% (AST 실측) |

**Pass 비율 19.0% → 52.4%, Fail 7 → 0.** 감사팀은 이 개선 폭을 보고서에서 누락했다. 정정한다.

### 6.2 [보강] CC 지표는 리메디에이션 전후가 동일하다는 사실을 병기해야 한다

R2 §6.3은 "CC>10 함수 비율 3.4%"를 2차 기준선으로만 제시했다. §2.2 B-2에서 확인했듯 **리메디에이션 전에도 3.4%였다**(백엔드 동일 도구 기준). 개선 추세로 오해될 수 있으므로 병기한다.

## 부록 — 재현 방법

§4.1/§4.2의 검사기, §5.5의 CC 측정, §5.4의 중복률 측정은 전부 **신규 의존성 없이** 동작한다(파서는 `node_modules/meriyah`, `lighthouse`의 기존 전이 의존성).

```bash
# 결함 유형 전수조사 + GET 쓰기 게이트
node <검사기> <저장소 루트>

# 리메디에이션 전후 비교 (임의 커밋에 대해)
git archive <commit> | tar -x -C /tmp/before && node <검사기> /tmp/before
```

감사 세션에서 사용한 스크립트는 일회성이며, CI 편입 시에는 `scripts/` 아래에 정식 배치하고 §4.2의 경고(게이트가 실제로 실패하는지 먼저 확인)를 반드시 이행할 것.
