## 0. 세 줄 요약

1. **규제가 아키텍처를 결정했다.** 📗 자동 연동(마이데이터)은 최소자본금 5억 원·법인 요건 때문에 개인사업자로 **불가능**하고, 무허가 영위는 5년 이하 징역 또는 5천만원 이하 벌금이다. 따라서 **현재의 수동입력 방식이 유지되며, "수동입력 UX를 모바일에서 얼마나 견딜 만하게 만드느냐"가 이 프로젝트 최대의 제품 과제가 된다**(§3.0).
2. **수익화는 "광고 선"을 넘지 않는 설계 문제다.** 📗 카드 추천 자체는 단순 광고·정보제공이면 등록 불요이지만, 발급계약 체결에 적극 관여하면 금소법 중개업 또는 여전법 모집인 등록 의무가 생기고 미등록 시 1년 이하 징역 또는 1천만원 이하 벌금이다. **경계를 코드와 문구 레벨에서 긋는 설계가 필요하다**(§5).
3. **기술 전환 비용은 이미 시계가 돌고 있다.** ADR 0005가 인증·세션·데이터 격리를 결정해뒀는데, 그때 133곳이던 `db.prepare`가 지금 **242곳**이다. M6~M14가 진행될수록 계속 늘어난다(§1.2).

### 1.2 ADR 0005 작성 시점 대비 증가폭

ADR 0005는 데이터 격리 비용을 이렇게 적었다: 테이블 11개, 라우트 18개, `db.prepare` 133곳.
지금은 테이블 약 20개, 라우트 23개, `db.prepare` **242곳**이다. **약 3~4개월 만에 격리 대상이 1.8배가 됐다.**

ADR 0005의 마이그레이션 1·2단계(센티널 사용자 생성 + 전 쿼리 `user_id` 스코프)는 **동작을 전혀 바꾸지 않으면서** 가장 비싼 작업을 끝내는 단계인데, 이 비용은 개발이 진행될수록 계속 늘어난다. ADR 0005도 같은 논리를 적어놨다 — *"서비스 전환을 결국 하지 않기로 해도 2단계까지의 작업은 손해가 아니다."*

반대 논리도 있다: 지금 스코프를 걸면 M6~M14의 모든 신규 쿼리가 `user_id`를 신경 써야 하고 리뷰 부담이 늘어난다. **트레이드오프이지 정답이 있는 문제가 아니다.** 다만 "나중에 하면 더 싸진다"는 시나리오만은 존재하지 않는다.

### 1.4 규제 관점에서 유리한 현재 설계

📗 보고서 기준으로 **이미 잘 되어 있는 것**도 짚어둘 필요가 있다.

- **가맹점 → 카테고리 자동 제안이 외부 API가 아니라 사용자 자신의 과거 거래 이력 기반이다** (`GET /api/transactions/suggest/category` — 본인 `transactions` 테이블에서 완전일치/부분일치 조회). 따라서 §2.4의 **가맹점 매핑 API 캐싱 제약(카카오·구글의 자체 DB 영구저장 금지)을 지금은 전혀 받지 않는다.** 외부 매핑 API를 도입하는 순간 이 제약이 새로 생긴다
- **카드 혜택 데이터(`card_benefits`, `card_products`)는 전부 사용자 수기 입력 설계다 — 크롤링 출처 없음(2026-08-04 확인).** 근거: 두 테이블은 마이그레이션 016·019가 스키마만 만들고, 데이터는 `src/routes/cardProducts.js`·`src/routes/cardBenefits.js`의 CRUD 라우트(GET/POST/PUT/DELETE)로만 들어온다. 두 라우트 어디에도 외부 HTTP 호출이 없고, 저장소에 시드 데이터·임포트 스크립트·크롤러가 없다. 실거래 DB 스냅샷 기준 두 테이블은 아직 생성 전(마이그레이션 미적용), 즉 실데이터 0건
  → **§2.4의 크롤링 판례 리스크(잡코리아·야놀자)를 현재는 전혀 받지 않는다.** 다만 이건 "리스크가 없다"가 아니라 **"리스크가 아직 발생하지 않았다"** 이다 — 카드 상품·혜택을 사용자가 전부 손으로 입력하는 건 현실성이 낮으므로, 이 데이터를 어떻게 채울지 정하는 순간 §2.4 제약이 그대로 온다(§9-4)

### 2.2 결제내역 수집 방식 — 3안 비교

| 항목 | (A) 수동입력 | (B) 마이데이터 | (C) CODEF/스크래핑 |
|---|---|---|---|
| 필요 라이선스 | 없음 (통신판매업 신고만) | 본인신용정보관리업 **허가** | 중개사 계약 (자사 허가 불요) |
| 최소 자본금 | 없음 | **5억원** (신용정보법 §6①1의4) | 없음 (CODEF 이용료) |
| **개인사업자 가능** | ✅ 가능 | ❌ **불가 (법인 전제)** | △ 가능 (API상 지원) |
| 초기 비용 | 수십만원~ | 수억원 (자본금+보안설비) | 확인 필요 (견적 기반) |
| 소요 기간 | 즉시 | 수개월 (예비허가+본허가) | 3영업일~ (계약 후) |
| 법적 리스크 | **낮음** | (진입 자체가 장벽) | 중~높음 (약관·재판매) |

**(A) 수동입력** — 사용자가 스스로 입력한 데이터를 처리하는 것은 신용정보법상 "신용정보업"이나 전자금융거래법상 "전자금융업"에 해당하지 않는다. 마이데이터 허가는 "신용정보제공·이용자 또는 공공기관으로부터 개인신용정보를 제공받는" 경우에 필요하므로 **직접 입력이면 허가 불요**.

단, 카드 결제내역(가맹점·금액·일시)은 신용정보법 제2조상 개인신용정보에 해당할 수 있다. 정보주체 본인이 입력·이용하는 구조라면 신용정보업 규제의 직접 대상은 아니지만, **서버에 저장하는 순간 개인정보보호법 의무는 전부 발생한다**(§2.5).

**(B) 마이데이터** — 허가 6요건: ① 최소자본금 5억원 ② 물적설비 ③ 사업계획 타당성 ④ 대주주 적격성 ⑤ 임원자격 ⑥ 전문성. **무허가 영위 시 5년 이하 징역 또는 5천만원 이하 벌금**(신용정보법 §50②1).
우회 경로: 마이데이터 사업자와 제휴해 정보주체 동의 기반 제3자 제공(신용정보법 §32)을 받거나 이용기관 지위로 참여. 단 재판매·화이트라벨은 엄격히 제한 — 개별 계약·법률검토 필요.

**(C) 스크래핑/CODEF** — 📗 보고서가 내 초안의 오류를 하나 교정한다:

> 2021년 개정 신용정보법이 금지한 것은 **"마이데이터 사업자가"** 접근매체(공동인증서, ID/PW)를 이용해 고객 신용정보를 수집하는 행위다. **마이데이터 허가를 받지 않은 자의 스크래핑을 직접 규율하는 조항은 아니다.** 다만 무허가로 신용정보를 수집·처리하면 신용정보업 무허가 영위 문제가 별도로 생길 수 있다.

→ 내 1차 초안은 이를 "마이데이터 시행 이후 스크래핑 전면 금지"로 단순화했었다. **부정확했고, 위 설명이 맞다.**

CODEF(헥토데이터)는 국내 최대 구독형 API 중개 플랫폼으로 카드 API를 개인사업자 형태로도 제공한다. 요금은 견적 기반(비공개). 인증정보를 중개사가 처리하므로 자사 보관 리스크는 낮아지지만, **카드사 회원약관과의 충돌·재판매 리스크는 남는다.**

### 2.3 수익모델 — 3안 규제 비교

| 조합 | 등록/라이선스 | 리스크 등급 |
|---|---|---|
| (가) 계산기 유료구독 | 통신판매업 신고 | 🟢 안전 |
| (다) 일반광고 | 통신판매업/사업자등록 | 🟢 안전 |
| (나) 카드추천 — **단순 광고·링크** | 없음 (경계 유지) | 🟡 주의 |
| (나) 카드추천 — **적극 중개** | 금소법 중개업 / 여전법 모집인 등록 | 🔴 위험 (미등록 시) |

**(가) 계산기 유료구독**
- 유료 구독 판매 시 **사업자등록 + 통신판매업 신고**(전자상거래법). 앱은 디지털콘텐츠 판매
- **금융상품자문업 경계**: 금소법 §2 4호의 금융상품자문업은 "금융상품의 가치·취득·처분결정에 관한 자문"이다. **사용자가 이미 보유한 카드의 혜택을 계산·분석하는 도구는 자문업에 해당하지 않을 가능성이 높다.** "이 카드를 발급받으라"는 권유로 넘어가면 경계에 근접

**(나) 카드추천 + 발급 제휴**
- **금소법 §12**: 이익 목적 반복적으로 계약체결을 "중개"하면 등록 대상. 금융위는 ① 설명의 정도 ② 계약체결에 미치는 영향 ③ 실무처리 관여도 ④ 이익발생 여부를 종합판단
- **여전법 §14의2·§14의3 (신용카드 모집인)**: 개인도 등록 가능하나 **카드사가 여신금융협회에 등록**하는 구조라 자기등록 불가. **1사 전속**(§14의5②, 소속 외 카드사 모집 금지, 위반 시 과태료 5천만원). 등록 전 1년 내 10시간 이상 교육 + 여신금융협회 자격시험. **무등록 모집은 1년 이하 징역 또는 1천만원 이하 벌금**(§70④)
- **온라인 링크 referral이 "모집"인지는 법적으로 미확정 회색지대.** 적극 중개면 등록 필요, 단순 광고·링크면 등록 불요로 해석되는 경향
- **제휴 플랫폼(링크프라이스 등) 경유해도 우회되지 않는다** — "모집/중개" 판단은 실질로 이뤄진다
- 자체 조사 보완: 여전법상 **연회비의 10%를 초과하는 경제적 이익을 제공하거나 제공 조건으로 회원을 모집하는 행위는 불법**이다. 즉 "발급하면 캐시백" 프로모션도 상한이 있다 (확실도 높음, 법령)

**(다) 일반광고**
- 계산기 앱에 AdMob 등 일반광고는 금융규제 대상 아님. **단 금융상품 광고(카드 발급 배너)를 넣으면 (나) 규제로 전환된다**
- 광고 SDK 사용 시 광고식별자·기기정보 수집을 개인정보처리방침·스토어 데이터 안전 섹션에 고지 필수

**⚠️ 1사 전속 조항의 함의**: 모집인 등록 경로를 택하면 **한 카드사만 모집할 수 있다.** "여러 카드를 비교해 최적을 추천한다"는 이 앱의 컨셉과 정면으로 충돌한다. 즉 **모집인 등록은 이 제품의 해법이 아니다.** 남는 선택지는 ① 광고 선을 지키거나 ② 금소법 판매대리·중개업 등록(법인 영역)이다.

## 3. 아키텍처 전환 옵션

### 3.0 규제가 확정한 것 — 수동입력 유지, 그리고 진짜 과제

**§2가 아키텍처 논의의 가장 큰 변수를 이미 닫았다.**

- 자동 임포트(은행·카드 자동 연동)는 마이데이터 허가 영역이고 **개인사업자로는 불가능**하다
- CODEF 경유는 이론상 가능하지만 견적 비공개·카드사 약관 리스크·재판매 제한이 있어 **초기 단계 선택지가 아니다**
- 따라서 **결제내역은 계속 사용자가 넣는다.** 현재 방식(카드사 CSV/엑셀 다운로드 → 웹 업로드)이 그대로 남는다

**여기서 나오는 결론은 하나다. 이 앱이 모바일 서비스로 성공할 수 있느냐는 인증도, 호스팅도, 차트도 아니고 "수동입력을 얼마나 안 아프게 만드느냐"에 달렸다.**

현재 임포트 경로는 데스크톱 전제다 — 카드사 홈페이지에서 엑셀을 내려받아 브라우저로 업로드한다. **모바일에서 이 흐름은 사실상 불가능하다.** 자동 연동이 막힌 상태에서 이 UX를 그대로 들고 가면, 앱은 출시돼도 쓰이지 않는다.

#### 수동입력 UX 개선 옵션 — 규제 안전성 기준으로 분류

| 방식 | 규제 | 기술 제약 | 평가 |
|---|---|---|---|
| **결제 알림 문자를 공유 시트로 붙여넣기** | 🟢 사용자가 직접 넘기는 것 = 수동입력 | iOS·Android 모두 가능, **권한 불요** | **가장 유력.** 사용자가 카드 결제 문자를 길게 눌러 "공유 → 가계부"로 보내면 파싱해서 거래 초안 생성 |
| **클립보드 감지** | 🟢 동일 | 앱 포그라운드 진입 시 클립보드에 결제 문자가 있으면 파싱 제안 | 유력. iOS 14+는 클립보드 접근 시 배너가 뜨므로 사용자에게 사전 고지 필요 |
| **SMS 자동 읽기** | 🟡 데이터는 수동입력 범주이나 스토어 정책이 별개 | **Android만 가능**(iOS는 SMS 읽기 불가). Google Play는 SMS 권한을 핵심 기능일 때만 허용하며 별도 선언 필요 | 반쪽짜리 + 심사 리스크. 확실도 **중간**, 확인 필요 |
| **영수증 촬영 OCR** | 🟢 | 카메라 권한. OCR 원가 발생 | 유력. §8.3의 프리미엄 기능과 동일. **가이드라인 4.2 네이티브 기능 요건도 동시 충족** |
| **카드사 앱에서 받은 파일을 "다른 앱으로 열기"** | 🟢 | iOS 문서 유형 등록 / Android intent-filter. **기존 `csvImport`·`cardImport` 파이프라인 그대로 재사용** | 유력. 개발 비용이 가장 낮다 |
| **위젯·빠른입력 (금액만 먼저, 분류는 나중)** | 🟢 | 홈 위젯 / Apple Shortcuts | 유력. 입력 마찰을 줄이는 정공법 |
| **자동완성·카테고리 제안 강화** | 🟢 자체 이력 기반이라 외부 API 제약 없음(§1.4) | 이미 구현됨 (`suggest/category`, `suggest/merchants`) | **이미 있는 자산.** 모바일에서 더 공격적으로 노출하면 됨 |
| **외부 가맹점 매핑 API 도입** | 🟡 §2.4 캐싱 제약 발생 | 카카오 건당 10원(2026 할인가) / 공공데이터 상권정보 | 도입하면 지금 없던 제약이 생긴다. 공공데이터 우선 |

**권고 조합(결정은 소유자 몫)**: 공유 시트 + 파일 열기 + 빠른입력 위젯을 1순위로, OCR을 프리미엄으로. SMS 자동 읽기는 Android 심사 리스크 대비 이득이 불확실하다.

> **이 절이 이 문서에서 가장 중요한 부분이다.** 나머지 아키텍처 논의(§3.1~3.4)는 전부 "어떻게 만드느냐"이고, 이 절만이 "무엇을 만드느냐"다.

### 3.1 인증·세션 — 이미 결정돼 있음

ADR 0005가 **서버 세션 + HttpOnly 쿠키(SQLite 세션 테이블)** 를 채택했다. JWT 기각, OAuth는 나중에 신원 출처로 얹는 것으로 정리.

모바일 앱이 생기면 ADR 0005의 재검토 트리거가 발동하지만, 재검토가 곧 번복은 아니다:

- **Capacitor/WebView 계열이면 쿠키 세션이 그대로 동작한다.** 같은 오리진을 WebView가 로드하므로 브라우저와 동일. 트리거가 형식적으로만 발동
- **React Native 재작성이면** 네이티브 fetch에서 쿠키 저장소를 다뤄야 하고, 키체인/Keystore에 토큰을 넣는 쪽이 자연스럽다. 이 경우 "짧은 액세스 토큰 + 서버 저장 리프레시 토큰" 하이브리드가 절충안 — ADR 0005가 JWT를 기각한 이유(즉시 무효화 불가)를 리프레시 토큰 서버 저장으로 해결하는 형태

**§3.4의 클라이언트 선택이 §3.1의 재검토 여부를 결정한다.**

### 3.2 데이터 격리 — 3가지 선택지

ADR 0005는 "테이블마다 `user_id` 컬럼(자식 테이블에도 비정규화)"을 채택하고 "사용자별 SQLite 파일 분리"를 기각했다. 기각 사유는 ① 마이그레이션을 사용자 수만큼 반복 ② `better-sqlite3` 동기 API의 파일 핸들 관리 ③ 백업/복원 의미 변화.

| 방식 | 장점 | 단점 | 확실도 |
|---|---|---|---|
| **A. `user_id` 컬럼 + 단일 DB** (ADR 0005 채택안) | 새 인프라 없음. 마이그레이션 1회. 이미 결정돼 있음 | **242곳 수정.** 조인 하나 빠뜨리면 타인 데이터 노출. 동기 API 동시성 병목 | 높음 |
| **B. PostgreSQL + Row Level Security** | DB가 격리를 강제 — 쿼리 실수해도 안 샌다. 동시성 해결 | SQL 방언 차이로 242곳 재작성 + 21개 마이그레이션 이식. 동기 코드가 전부 async → 사실상 백엔드 전면 개편 | 높음 |
| **C. 사용자별 DB (Turso/libSQL 등)** | 물리적 격리. SQLite 방언 유지 → **242곳을 안 고쳐도 됨** | 외부 SaaS 종속. 마이그레이션 전파를 직접 스크립트로. **§2.5 국외이전 문제** | 중간 |

**주목**: ADR 0005가 "사용자별 DB 파일"을 기각한 세 사유 중 ①②는 관리형 libSQL이 바로 그 문제를 풀려고 만들어진 제품이다. ③(백업/복원 의미 변화)은 여전히 유효하다. ADR 번복이 아니라 **재검토 트리거에 "관리형 per-tenant SQLite 플랫폼의 성숙"을 추가할 근거**는 된다.

핵심 교환: **옵션 A는 242곳을 고치되 실수 시 데이터가 새고, 옵션 C는 안 고치되 벤더·국외이전 위험이 생긴다.**

### 3.3 백엔드 호스팅

현재는 `node src/server.js` 단일 프로세스 + 로컬 파일. 서비스가 되려면 최소한: HTTPS 종단, 상시 가동, 자동 백업, 로그·모니터링, 배포 파이프라인(앱 심사가 붙으면 클라이언트·서버 버전 스큐가 상시 존재).

**호스팅 선택은 §2.5 국외이전과 묶여 있다.** 해외 리전에 한국 사용자 개인정보를 두면 개인정보보호법 §28의8의 고지·동의 의무가 발생한다. 국내 리전(AWS 서울, NCP 등)이면 이 논점이 사라진다. 해외 PaaS(Fly.io, Render, Railway)가 편하지만 이 문제를 떠안는다.

📗 보고서는 1단계 착수 비용을 **수십만~수백만원**(사업자등록·앱 등록비·서버·디자인)으로 잡는다. 이건 앞선 자체 추정보다 근거 있는 숫자다.

**추가 권고(📗)**: "개인정보 최소수집 원칙 — 서버 저장을 최소화하고 온디바이스 처리 우선". **이 앱은 원래 온디바이스(로컬 SQLite)로 만들어졌다는 점이 규제상 자산이다.** §8.10(셀프 호스팅 프리미엄)과 연결된다.

### 3.4 모바일 클라이언트 — 4가지 선택지

현재 프론트엔드는 React 19 + Vite 8 + Tailwind v4 + Recharts 3 + wouter.

| 방식 | 코드 재사용 | 앱스토어 통과 | 주요 리스크 |
|---|---|---|---|
| **A. PWA만** | 100% | **불가** — 스토어 배포 안 됨 | "정식 앱 출시" 목표와 불일치 |
| **B. Capacitor 래핑** | 거의 100% | 가능하되 **가이드라인 4.2 리스크** | 네이티브 레이어 없으면 "repackaged website" 반려 |
| **C. React Native 재작성** | **12,924 LOC 전면 재작성** | 가장 안전 | 비용 압도적. Recharts·Tailwind 못 씀 |
| **D. 하이브리드** (네이티브 셸 + WebView 화면) | 대부분 재사용 | B보다 안전 | 두 스택 유지 |

**가이드라인 4.2(Minimum Functionality)가 B의 핵심 리스크다.** 리뷰어가 보는 신호: 브라우저 UI 잔재, 네이티브 내비게이션 부재, 푸시·생체인증 미사용, 표준 오프라인 에러 화면.

**여기서 §3.0과 §3.4가 맞물린다.** 수동입력 UX 개선을 위해 필요한 기능들 — **공유 시트 수신, 파일 열기 인텐트, 카메라 OCR, 홈 위젯, 푸시 알림** — 이 정확히 가이드라인 4.2가 요구하는 "네이티브다움"이다. **규제 때문에 어쩔 수 없이 해야 하는 일이, 심사 통과에 필요한 일과 같다.** 이 프로젝트에서 드물게 운이 좋은 지점이다.

**권고(결정은 소유자 몫)**: B(Capacitor) + §3.0의 네이티브 입력 경로 3~4개 → 반려 시 D로 보강. C는 "RN이어야만 하는 이유"가 생기기 전에는 근거가 약하다.

- 카드 발급 링크는 **"광고"임을 명시**하고 발급계약 체결에 적극 관여하지 않는다
- **"이 카드를 발급받으세요" 류의 권유 문구를 배제**한다. 계산·분석 결과 제시까지만
- 수수료 구조가 "중개"로 해석될 여지가 있으면 **금융위 유권해석 또는 법률검토 후 진행**
- 제휴 플랫폼(링크프라이스 등) 경유로는 우회되지 않는다

**엔지니어링 관점의 함의**: 이 경계는 문구 하나로 넘나들 수 있다. **"권유 문구 금지"를 코드 리뷰 체크리스트나 카피 가이드(`docs/VOICE_TONE_GUIDE.md`)에 명문화하지 않으면, 나중에 아무 생각 없이 추가한 CTA 버튼 하나가 등록 의무를 만든다.** 이건 기술 부채가 아니라 법적 부채다.

### 5.3 일반 광고 네트워크 (AdMob 등)

- **AdMob이 "금융 앱 카테고리"를 제한한다는 정책은 확인되지 않았다.** 제한은 광고주 쪽에 걸린다(예: 미국 APR 36% 이상 개인대출 광고 금지). 퍼블리셔로서 가계부 앱이 배제되는 규정은 없음 — 확실도 **중간**(부재 증명)
- 퍼블리셔는 AdSense 프로그램 정책 준수 의무. 위반 시 게재 중단·계정 정지
- 📗: 광고 SDK 사용 시 광고식별자·기기정보 수집을 개인정보처리방침과 스토어 데이터 안전 섹션에 고지 필수

**수익 규모 감** — 확실도 **낮음** (업계 블로그 추정치):
- Tier 1 배너 eCPM $1.50~$4.00. DAU 3만 가계부 앱에서 배너만으로 월 $600~900 추정
- ATT 옵트인률 2026년 글로벌 27%(US 31%, EU 22%, JP 38%)에서 정체. 미동의 트래픽 eCPM 20~40% 낮음
- 한국은 impression 단가가 높은 편

**현실 감각**: DAU 3만은 개인 앱으로 도달하기 매우 어렵다. DAU 1,000이면 월 $20~30 수준이다. **광고를 주 수익원으로 설계하는 건 규모의 게임이고 초기 단계에는 맞지 않는다.** §6(구독)이 1단계의 현실적 축이다.

## 6. 수익화 — 구독

### 6.1 한국 사업자로서의 선행 요건 (📗)

- **사업자등록 + 통신판매업 신고**(전자상거래법) — 유료 앱·구독은 디지털콘텐츠 판매이므로 필수
- 업종코드: "응용 소프트웨어 개발·공급업" 또는 "포털 및 기타 인터넷 정보매개서비스업" — **정확한 코드는 관할 세무서·홈택스 확인 필요**
- **전자상거래법 §17 청약철회**: 디지털콘텐츠는 제공 개시 시 청약철회를 제한할 수 있으나, **그 사실을 사전에 명확히 고지하고 시험사용 등 조치를 해야 한다**(§17⑥). 미고지 시 철회 가능
  → **실무 번역: 구독 결제 화면에 "결제 즉시 이용 개시되며 청약철회가 제한됩니다"를 명시하고, 무료 체험 또는 일부 기능 시험사용을 제공해야 한다.** 이건 UI 요구사항이다

### 6.2 앱스토어 수수료 (2026-08)

| 항목 | 값 | 확실도 |
|---|---|---|
| Apple 기본 | 30% | 높음 |
| **Apple Small Business Program** | **15%** — 전년도 App Store 수익 $1M 미만 | 높음 |
| Apple 구독 2년차 이후 | 15% (일반) | 중간 |
| Google Play 구독 | 기존 15% | 높음 |
| Google Play 2026-06-30 이후 (US/UK/EEA) | 서비스 수수료 10%(연 $1M까지) + Play 결제 시 빌링 5%. Epic 합의로 구독 15%→10% | **중간 — 재확인 필요. 한국 적용 여부 불명** |
| 한국 제3자 결제 (전기통신사업법) | Apple: StoreKit External Purchase Entitlement(한국 전용). Google: 자체 결제 시 **최대 26%** | 중간 |

**한국은 인앱결제 강제 금지법이 있어 제3자 결제를 붙일 수 있지만, 26% + PG 수수료(2~3%)면 30%와 비슷해진다. Small Business Program 15%를 받을 규모라면 그냥 인앱결제가 유리하다.**

### 6.3 무료/유료 티어 분할

경쟁 앱 가격대 (2026, 해외):

| 앱 | 가격 | 무료 티어 |
|---|---|---|
| YNAB | $14.99/월, $109/년 | 없음 (34일 체험) |
| Monarch Money | $14.99/월, $99.99/년, Plus $199/년 | 없음 (7일 체험) |
| Copilot Money | $13/월, $95/년 (iOS/macOS 전용) | 없음 |

**해외 주요 앱은 영구 무료 티어를 두지 않는다.** 반면 국내 가계부 앱은 무료 + 광고/중개 수수료 모델이 지배적이다. **시장이 갈려 있고, 국내 무료 모델의 수익원(중개 수수료)이 §2에서 막혀 있다는 게 이 프로젝트의 특수 상황이다.**

→ **역설적으로, 규제 제약이 "무료+광고"보다 "구독" 쪽을 밀어준다.** 광고는 규모가 있어야 하고(§5.3) 카드 중개는 막혀 있으니, 개인사업자 1단계에서 실질적으로 남는 축은 구독이다.

| 분할 축 | 무료 | 유료 | 적합도 |
|---|---|---|---|
| 데이터 보관 기간 | 최근 1년 | 무제한 | 낮음 — 가계부는 과거 데이터가 핵심 가치 |
| **분석 깊이** | 기본 집계 | 예측·시뮬레이션·비교분석 | **높음** — Simulator·Comparison이 이미 있음 |
| **자동화·입력 편의** | 수동 입력 | OCR·자동 분류·알림 | **높음** — §3.0과 직결 |
| **원가가 실제로 드는 기능** | — | AI 분석, OCR | **높음** — 과금 정당화가 쉽다 |
| 가족/공유 | 개인 | 가족 계정 | 중간 |
| 내보내기 | CSV | 엑셀·PDF 리포트 | 중간 |
| 광고 제거 | 광고 있음 | 광고 없음 | 낮음 — 단독으로는 단가를 못 받음 |

**패턴 관찰**: 구독이 잘 붙는 축은 "무료 사용자에게서 뭘 뺏는 것"이 아니라 **"유료 사용자에게 원가가 드는 것을 주는 것"** 이다. 전자는 이탈을 부르고 Apple 3.1.2(a)의 "기존 유료 기능 회수 금지"에도 걸릴 수 있다.

**⚠️ 다만 §3.0과 충돌 주의**: 입력 편의 기능(공유 시트, 파일 열기, 빠른입력)을 유료로 막으면 **무료 사용자는 앱을 아예 못 쓴다.** 자동 연동이 없는 앱에서 입력 경로는 기본 기능이다. **유료화는 OCR처럼 원가가 드는 것에 한정하고, 기본 입력 경로는 무료로 두는 게 맞다.**

### 6.4 구독 도입 시 기술 요구사항

- 영수증 검증(서버 사이드) — Apple App Store Server API / Google Play Developer API
- 구독 상태를 서버 DB에 반영 (두 플랫폼 상태를 하나의 엔티티로 통합)
- 갱신/취소/환불/유예기간 웹훅 처리
- 크로스 플랫폼 복원 (Apple 3.1.2(a) "모든 기기에서 동작")
- **구독을 붙이는 순간 결제 상태 정합성이 새로운 버그 표면이 된다.** 이 저장소가 이중계산 방지에 들인 공을 생각하면, 같은 수준의 주의가 필요한 영역이다

## 7. 보안 / 컴플라이언스

### 7.1 이 앱의 데이터가 무엇인지

**이 앱은 카드번호·계좌번호·인증정보를 저장하지 않는다.** 저장하는 건 거래 기록(날짜/금액/가맹점/카테고리/결제수단 이름)이다.

- 카드번호를 안 다루므로 **PCI DSS 비대상**
- 자금 이동이 없으므로 **전자금융거래법상 전자금융업 등록 비대상** (📗 확인)
- 거래 내역은 신용정보법 §2상 개인신용정보에 해당할 수 있으나, **정보주체 본인이 입력·이용하는 구조면 신용정보업 규제의 직접 대상은 아니다** (📗)
- **개인정보보호법은 대상이다** — §2.5 참조

📗이 확정한 결론: **"사용자가 직접 입력한 거래 기록"과 "금융회사에서 자동 수집한 거래 기록"은 법적 취급이 완전히 다르다.** 전자를 유지하는 설계가 규제 부담이 비교 불가능하게 가볍다.

### 7.2 한국 — 실무 체크리스트 (§2.5 요약)

- [ ] 개인정보처리방침 수립·공개 (§30) — 앱 내 링크 + 스토어 메타데이터
- [ ] 안전성 확보조치 (§29, 고시 시행 2025.10.31) — 접근권한 관리, 암호화, 접속기록 보관
- [ ] CPO 지정 (§31)
- [ ] 국외이전 고지·동의 (§28의8) — 해외 리전 사용 시. **국내 리전이면 회피 가능**
- [ ] 개인정보 최소수집 — 온디바이스 처리 우선 (📗 권고)
- ISMS: 소규모 착수 단계 비대상. 성장 시 임계값 재확인

### 7.3 GDPR (해외 사용자를 받는 경우)

- **EU 대표자(Art. 27)**: EU에 사업장 없이 EU 거주자를 대상으로 서비스하면 지정 의무. 위반 시 최대 €1,000만 또는 전세계 매출 2%
- **DPO**: 대규모 체계적 모니터링·대규모 민감정보 처리가 아니면 불필요. 이 규모에서는 대체로 불필요
- 확실도 **중간**

**실무적 함의: 초기 출시를 한국으로 제한하면 GDPR 부담을 통째로 미룰 수 있다.** 스토어에서 출시 지역을 선택하면 되므로 설정 하나로 가능한 통제다. **📗의 1단계(개인사업자, 국내 시장)와도 정확히 맞물린다.**

### 7.4 저장 데이터 암호화 — 아직 결정 안 된 항목

ADR 0005가 명시적으로 "이 ADR이 결정하지 않는 것"에 넣어둔 항목이다. 서비스 전환을 진지하게 검토한다면 **별도 ADR이 선행돼야 한다.**

| 방식 | 특징 |
|---|---|
| 디스크 레벨 암호화 (호스팅 제공) | 가장 쉬움. 서버 침해 시 무력 |
| SQLCipher / libSQL 암호화 | DB 파일 전체 암호화. 키 관리가 관건 |
| 애플리케이션 계층 필드 암호화 | 금액·가맹점만 선택 암호화. 집계 쿼리가 서버에서 불가능 → **대시보드 전면 재설계** |
| 클라이언트 사이드 E2E | 가장 강한 보장이자 최고의 마케팅 포인트. **서버 집계·AI 분석 전부 불가능** |

**E2E와 AI 분석은 근본적으로 충돌한다.** 다만 📗의 "온디바이스 처리 우선" 권고와 이 앱의 로컬 태생을 생각하면, **E2E 또는 온디바이스 중심 설계가 규제 부담을 가장 크게 줄이는 선택지이기도 하다.** 제품 정체성의 결정이다.

> 사용자 메모리 규칙: "Production DB: AES-256-GCM encryption required."

## 8. 프리미엄 기능 아이디어

각 항목에 구독 적합성과 규제/기술 제약을 붙였다. 규제 등급은 §5.1 기준.

### 8.1 지출 예측 & 월말 잔액 시뮬레이션 🟢
반복거래 규칙 + 할부 잔여 스케줄 + 과거 패턴으로 "이번 달 말 잔액"을 예측.
- **구독 적합성**: `recurring_rules`, `installments`, `Simulator`가 이미 있다. **가장 적은 추가 개발로 만들 수 있는 유료 기능.** 매달 확인하게 되므로 리텐션과 궁합이 좋다
- **제약**: 없음. 자체 데이터만 씀. 📗 기준으로도 "계산기" 범주 = 안전

### 8.2 AI 지출 분석 리포트 🟢 (기술·고지 제약)
LLM으로 월간 소비 패턴을 요약하고 이상 지출을 짚어준다.
- **구독 적합성**: **호출당 실제 원가 발생** → 과금 정당화가 가장 쉬운 유형(§6.3)
- **제약**: Apple 5.1.2가 제3자 AI 공유를 명시적 동의 대상으로 규정. Google Play도 2026년에 User Data 요구사항이 제3자 AI 통합에 적용됨을 명확화. **§2.5 국외이전 문제도 발생한다 — 해외 LLM API에 거래 데이터를 보내면 개인정보 국외이전이다.** 처리방침 기재 + 동의 필요. §7.4 E2E와 양립 불가
- **주의**: "이 카드를 발급받으라"는 결론을 AI가 생성하면 §5.1의 🔴 영역으로 넘어간다. **프롬프트·출력 필터링에 규제 경계를 반영해야 한다**

### 8.3 영수증 촬영 자동 입력 (OCR) 🟢 ★
카메라로 영수증을 찍으면 날짜·금액·가맹점을 파싱해 거래 등록.
- **구독 적합성**: OCR API 원가 발생 + **§3.0의 수동입력 UX 과제를 직접 해결** + **§3.4 가이드라인 4.2 네이티브 기능 요건 충족.** 일석삼조
- **제약**: 한국 영수증 포맷 특화 튜닝 필요. 정확도가 낮으면 수동 입력보다 느려서 역효과. 클라우드 OCR이면 §2.5 국외이전 검토(온디바이스 OCR — iOS Vision, Android ML Kit — 이면 회피)

### 8.4 카드 혜택 최적화 추천 🟢 / 🔴 (경계가 갈린다)
- **🟢 "보유 카드 중 최적 결제수단"**: "이 결제는 A카드 대신 B카드로 했으면 3,200원 절약". **📗 기준으로 금융상품자문업 아님 — 안전지대.** `card_benefits`, `card_products` 테이블이 이미 있다. **절약액이 구독료를 넘으면 가치 증명이 자명한, 가장 설득력 있는 유료 기능**
- **🔴 "새 카드 발급 추천 + 수수료"**: 중개·모집 영역. §5.1 참조
- **경계를 코드로 긋는다**: 추천 대상을 `payment_methods`에 등록된 **보유 카드로 한정**하면 기술적으로 안전지대에 머문다. 미보유 카드를 추천 결과에 넣는 순간 회색지대로 들어간다. **이건 데이터 모델 레벨의 구분이므로 설계 시점에 결정해야 한다**
- **⚠️ 진짜 병목은 규제가 아니라 데이터 확보다**: 현재 혜택 데이터는 100% 사용자 수기 입력이고 실데이터는 0건이다(§1.4). 이 기능이 성립하려면 카드 상품·혜택 DB를 누군가 채워야 하는데, §2.4에 따르면 B2B 라이선스는 사실상 없고 크롤링은 판례 리스크가 크다. **남는 경로는 ① 사용자가 자기 카드만 직접 입력(현재 설계, 확장 안 됨) ② 카드사 공식 제휴 ③ 운영자가 수동 큐레이션**뿐이다. ③이 현실적이지만 카드사 상품설명서를 그대로 재현하면 저작권·DB권 문제가 생기므로 **"혜택의 사실"만 자체 표현으로 정리해야 한다**(사실은 저작권 밖, 표현·편집물은 보호 대상)

### 8.5 가족 공유 가계부 🟢
가구 단위 통합 가계부. 구성원별 지출 분리 + 공동 예산.
- **구독 적합성**: 좌석 기반 과금이 자연스럽고, 한 명이 결제하면 나머지가 묶여 **이탈률이 구조적으로 낮다**
- **제약**: 데이터 모델이 "사용자 소유"에서 "가구 소유 + 사용자 귀속"으로 바뀐다. **ADR 0005의 `user_id` 스코프를 설계할 때 `household_id`까지 고려하면 공짜, 나중에 하면 비싸다**
- **규제**: 타인의 거래 데이터를 보게 되므로 구성원 각자의 동의 처리가 필요. 개인정보 제3자 제공 논점

### 8.6 예산 초과 알림 / 결제일 리마인더 🟢 ★
카테고리 예산 80%·100% 도달 알림, 카드 결제일 3일 전 잔액 부족 경고.
- **구독 적합성**: 단독 유료화는 약하다. **푸시 알림은 §3.4 가이드라인 4.2 대응의 1순위 요소이므로 무료로 주고 심사 통과에 쓰는 게 낫다**
- **제약**: 서버 스케줄러 + FCM/APNs. `categories.monthly_budget`이 이미 있음

### 8.7 다년치 비교 리포트 / 세무용 내보내기 🟢
연도별 추이, 카테고리별 장기 트렌드, 세무 신고용 집계 엑셀·PDF.
- **구독 적합성**: 연말·연초 집중 수요 → **연간 구독 유도에 유리.** 프리랜서·개인사업자는 지불 의사가 뚜렷
- **제약**: 없음. `Comparison` 페이지·`export` 라우트가 이미 있다. **세무 "자문"으로 넘어가지 않도록 집계·서식까지만**

### 8.8 구독 서비스 자동 탐지 & 해지 리마인더 🟡
반복 결제를 탐지해 "잊고 있던 구독" 목록 생성, 무료체험 종료 전 알림.
- **구독 적합성**: 절약액이 즉시 보인다. `recurring_rules`·`recurring_occurrences` 재사용 가능
- **제약**: **해지 대행까지 하면 계약 대리 영역.** 탐지·알림까지만 하면 안전

### 8.9 목표 기반 저축 플래너 🟢 / 🔴
"3년 뒤 전세금 1억" 목표 입력 → 월 저축액 역산 + 진행률 추적.
- **구독 적합성**: 장기 목표라 **구독 기간 자체가 길어진다.** `savings_products`, `Simulator` 재사용
- **제약**: ⚠️ **특정 금융상품(적금·펀드) 추천은 금소법 자문/중개 영역.** "얼마를 모아야 하는가"까지만, "어디에 넣어야 하는가"는 하지 않는 선이 안전선. §8.4와 같은 구조의 경계다

### 8.10 데이터 소유권 / 셀프 호스팅 라이선스 🟢
프리미엄 사용자에게 로컬 실행 바이너리 또는 Docker 이미지 + 완전한 데이터 내보내기 제공.
- **구독 적합성**: **이 앱의 출신이 그대로 상품이 된다.** "당신 데이터는 당신 서버에" — 개발 비용이 거의 0(이미 그 형태로 존재하는 앱). **📗의 "온디바이스 처리 우선" 권고와도 정확히 일치하고, 서버 저장을 줄이면 §2.5 의무도 줄어든다**
- **제약**: Apple 3.1.1(앱 내 기능 잠금 해제는 IAP 필수) 해석이 갈린다 — 확실도 **낮음**. **웹사이트에서 별도 판매하는 형태가 안전**

### 8.11 정산/더치페이 자동화 🟡
여러 명이 쓴 지출을 자동 분개하고 정산 내역 생성. (M11 #289 settlement 작업과 연결)
- **구독 적합성**: 그룹 기능이라 **자연 확산**이 있다
- **제약**: ⚠️ **실제 송금 기능을 붙이면 전자금융거래법 영역이다.** 정산 금액 계산까지만 하고 송금은 외부 앱 딥링크로 넘기면 안전

### 8.12 소비 습관 챌린지 🟢
"이번 달 카페 지출 20% 줄이기" 목표, 달성 배지, 익명 비교 통계.
- **구독 적합성**: 리텐션 장치. 단독 유료화는 약하나 **해지율을 낮추는 부가 기능**
- **제약**: 익명 비교 통계는 타 사용자 데이터 집계가 필요 → 이용 목적 명시·동의 필요. §7.4 E2E와 충돌

## 9. 미해결 질문 — 결정이 필요한 순서대로

§2가 들어오면서 **1·2번이 사라지고 새 질문이 생겼다.**

1. ~~자동 연동을 할 것인가~~ → **📗이 닫음. 개인사업자로는 불가.** 대신: **§3.0의 수동입력 UX 개선안 중 무엇을 1차로 만들 것인가**
2. ~~법인으로 갈 것인가~~ → **📗이 닫음. 1단계는 개인사업자로 충분.** 대신: **Play Console을 개인사업자 등록번호로 조직 계정 개설이 가능한가**(12명 테스트 규칙 면제 여부, §4.1) — **확인 필요**
3. **카드 혜택 추천을 "보유 카드 한정"으로 못 박을 것인가** → 못 박으면 규제 안전지대에 영구히 머문다. 열어두면 나중에 중개 등록 논의가 따라온다 (§8.4)
4. ~~카드 혜택 데이터의 현재 출처는 무엇인가~~ → **확인 완료(2026-08-04). 100% 사용자 수기 입력, 크롤링 없음, 실데이터 0건** (§1.4). 대신 새 질문: **카드 상품·혜택 DB를 누가 어떻게 채울 것인가** → 사용자 자율 입력이면 §8.4 기능이 확장되지 않고, 운영자 큐레이션이면 §2.4 저작권·DB권 경계를 지켜야 하며, 카드사 제휴면 §5.1의 광고/중개 경계로 되돌아온다. **세 경로 모두 다른 문제로 이어지므로 §8.4를 진지하게 검토할 때 함께 결정해야 한다**
5. **클라이언트: Capacitor인가 React Native인가** → §3.1 인증 방식이 여기 종속된다. §3.0의 네이티브 입력 경로가 어느 쪽이든 필요하다는 점은 동일
6. **저장 데이터 암호화 수준 / 온디바이스 비중** → E2E를 고르면 §8의 AI·집계 기능이 대부분 불가능해진다. 별도 ADR 필요 (§7.4)
7. **ADR 0005 1·2단계를 지금 할 것인가** → 지금이 가장 싸고, M6~M14가 진행될수록 비싸진다 (§1.2)
8. **출시 지역** → 한국만 열면 GDPR을 미룰 수 있다 (§7.3). 📗의 1단계와 일치

## 10. 만약 진행한다면 — 순서 스케치

계획이 아니라 **의존관계 스케치**다. 착수 결정 시 별도 기획이 필요하다.

```
[0단계] 결정 — §9. 법률검토(📗 Caveats의 6개 항목) 포함. 코드 변경 없음
   ↓
[1단계] ADR 0005 1·2단계 (users 테이블 + 242곳 user_id 스코프)
        → 동작 변화 없음. 서비스 전환을 안 하기로 해도 손해 아님
   ↓
[2단계] ★ 수동입력 UX 프로토타입 — 공유 시트 수신 / 파일 열기 / 빠른입력
        → 규제가 자동 연동을 막았으므로 이게 제품 성패를 가른다.
          웹에서 먼저 검증 가능한 부분(파싱 로직)은 앞당길 수 있다
   ↓
[3단계] 저장 암호화 ADR + 인증 3·4단계 (세션·로그인·CSRF 강화·레이트리밋)
   ↓
[4단계] 백엔드 호스팅 + HTTPS + 백업 + 모니터링. 국내 리전 우선.
        AUTH_MODE=multi 실사용 검증
   ↓
[5단계] 모바일 클라이언트 (Capacitor + 2단계의 네이티브 입력 경로)
   ↓
[6단계] 사업자 준비 — 개인사업자 등록, 통신판매업 신고,
        개인정보처리방침 + CPO 지정, Data Safety / 금융기능 신고,
        계정 삭제 기능, (개인 계정인 경우) 12명 테스트
   ↓
[7단계] 수익화 — 구독 먼저(규제 안전). 광고는 규모 확보 후.
        카드 추천은 "보유 카드 한정 + 광고 선" 확정 후
```

**1·2단계는 다른 모든 단계와 독립적으로 지금 착수 가능하다.** 특히 2단계의 파싱 로직(결제 문자 → 거래 초안)은 현재 웹앱에서도 그대로 쓸 수 있으므로, 서비스 전환을 안 하기로 해도 손해가 아니다 — 1단계와 같은 성질이다.
