## 0. 왜 인계하는가

이 세션이 **1,688턴을 넘겼다.** 기능 결함이 있어서가 아니라 길이 때문이다.

턴이 길어지면 앞부분이 요약으로 접히고, 접힌 자리에 **오늘 확정한 도메인 규칙과
그 근거**가 들어 있다. 근거가 사라진 규칙은 다음 세션에서 "왜 이렇게 했지" 로
바뀌고, 그때 되돌리면 오늘 고친 버그가 그대로 되살아난다. 실제로 이번 사이클에서
그 계열의 사고를 한 번 겪었다(§2.1).

그래서 **접히기 전에 문서로 내린다.**

### 1.1 무엇을 만들었나

기존 거래의 결제 방식(`settlement`)을 결제수단 단위로 일괄 재분류하는 도구.
**프리뷰 → 확인 → 실행** 2단계(ADR 0008).

```
POST /api/settlement/reclassify/preview   무엇이 몇 건, 잔액이 어떻게. DB 안 바꿈
POST /api/settlement/reclassify           지문(preview_token) 확인 뒤에만 쓴다
```

- `src/services/settlementReclassify.js` — 계획 수립·실행
- `src/routes/settlement.js` — 두 엔드포인트
- `client/src/components/SettlementReclassifySection.jsx` — 설정 화면
- `client/src/lib/settlementLabels.js` — 내부 값 → 사용자 문구

### 1.2 확정한 설계 결정 (되돌리기 전에 읽을 것)

**a. 선례를 따랐다 — `CardRemapSection.jsx`(305줄) 구조**

#401 의 카드 재매핑 도구가 이미 같은 문제를 풀어 뒀다. 새로 짓지 않고 그 구조를
그대로 가져왔다.

- `preview_token = plan.fingerprint` 로 프리뷰 이후 변화를 감지
- 조건이 바뀌면 300ms 디바운스 후 프리뷰 재요청, `seq` 로 늦은 응답 무시
- 지문 없음 → **428**, 지문 불일치 → **409**

**b. 프리뷰와 실행이 같은 함수를 부른다**

두 엔드포인트가 모두 `planReclassify` 를 부른다. ADR 0008 이 비용으로 명시한 지점
이다 — *"실행 로직과 프리뷰 로직이 갈라지면 둘이 어긋날 수 있다."*

**c. 잔액 영향을 손으로 유도하지 않는다**

실제 `computeBalance` 를 **두 번** 돌린다(지금 행 / 바꾼 행). `deferred` 제외 ·
수입지출 방향 · 기준일 · 개설일 경계가 얽혀 있어 약식 계산은 경계에서 틀린다.

**d. 지문에 각 행의 현재 `settlement` 까지 넣는다**

뮤테이션 테스트에서 살아남아 발견한 진짜 구멍이다. id·금액만 담으면 **프리뷰 뒤에
대상 중 한 건의 상태만 바뀐 경우** 건수도 id 목록도 그대로라 지문이 통과한다.
사용자가 본 적 없는 상태의 거래가 조용히 재분류된다. 회귀 테스트 `C-3b`.

**e. 늘어난 잔액은 돈이 생긴 게 아니다**

`deferred` 로 바꾸면 잔액이 늘지만 그만큼 카드 미결제액이 는다. 실거래 사본에서
두 숫자가 **정확히 일치**했다. 잔액만 보여주면 사용자가 반대로 읽으므로 같은
줄에서 말한다. 확인 대화상자에도 이 문장이 들어간다 — 건수만 물으면 **무엇을
승인하는지 모른 채 승인한다.**

## 2. 이번 사이클 도메인 함정 — 재발 방지

### 2.1 전월실적 기간 ≠ 청구 이용기간 ⚠️ 최우선

**이번 사이클에서 가장 비쌌던 실수다. 되돌리지 말 것.**

| | 무엇을 정하나 | 기준 |
|---|---|---|
| 결제일별 **이용기간** | 이번 달에 **얼마를 청구**하나 | 결제일마다 다르다 |
| **전월실적 산정기간** | 혜택 **자격**을 채웠나 | **전월 1일 ~ 말일 (달력월)** |

처음에 실적을 `statement_close_day`(마감일) 기준 구간으로 잡았다. **틀렸다.**
사용자가 실사용 중 제기해 조사한 결과 달력월이 맞았다.

근거는 관행 그 자체다. 사람들이 결제일을 12·13·14·15일로 맞추는 이유가 **실적이
달력월로 고정이라서** 청구 이용기간을 거기 맞추려는 것이다. 실적이 결제일을
따라간다면 이 관행이 성립할 이유가 없다.
(권장 결제일: 현대 12 / 삼성·하나·BC 13 / 신한·롯데·KB·우리·NH 14 / 기업 15)

실거래로 잰 오차 — **판정이 뒤집혔다.**

```
결제일 25일 카드, 2026-02 기준, 실적조건 400,000원
  마감일 기준 01-12 ~ 02-11  →  321,394원  "미달"    ← 틀림
  전월 달력월 01-01 ~ 01-31  →  403,054원  "충족"    ← 맞음
```

사용자가 자격을 채웠는데 앱이 "실적을 못 채웠어요" 라며 그 카드를 추천에서
떨어뜨린다. `test/cardThreshold.test.js` 의 `describe('E. ...')` 가 이 금액을 그대로
회귀 테스트로 고정하고 있다.

**따라서:**
- `cardThreshold.prevPeriodFor(asOf)` 는 **카드 정보를 받지 않는다.** 인자를 다시
  추가하지 말 것 — 받으면 언젠가 누가 그걸 쓴다
- `cardBilling.billingMonthFor` 는 **청구월**이라 결제일·마감일 기준이 맞다.
  **두 함수를 같은 규칙으로 통일하려 들면 안 된다**
- `period.resolved` 를 되살리지 말 것. 달력월은 언제나 정확히 정해져 "못 풀었다"
  상태가 없다. 남기면 화면이 "마감일을 설정하면 정확해집니다" 라는 **틀린 안내**를 한다

카드사별 예외(전표 접수일 기준 등)는 확인된 사례가 없어 `threshold_period_type`
컬럼을 넣지 않았다. 실제 예외 카드가 확인되면 그때 별도 이슈로 연다.

### 2.2 `NULL` 의 뜻이 두 가지면 되짚기가 틀린다

`transactions.card_product_id` 가 `NULL` 인 이유가 둘이다.

| NULL 의 뜻 | 결제수단으로 되짚어도 되나 |
|---|---|
| 한 번도 지정된 적 없다 | 된다. 후보가 하나면 그 카드가 맞다 |
| **사용자가 그 카드를 지웠다** | **안 된다.** 지운 카드가 후보에서 빠져 남은 하나가 정답처럼 보인다 |

카드 삭제 시 `card_product_id` 를 `NULL` 로 되돌리면, 같은 결제수단에 남은 다른
카드로 **과거 지출이 통째로 넘어간다.** 이슈 #410 으로 등록했고 별도 세션이
#411·#412·#413 으로 **삭제 대신 비활성화**로 바꿔 해결했다.

**따라서:** `loadCards()` 는 비활성 카드도 싣는다. 빼면 "그 결제수단에 상품이 딱
하나" 조건이 성립해 같은 버그가 되살아난다. 추천 후보에서 빼는 것은 계산 쪽의
몫이지 목록에서 지우는 게 아니다.

### 2.3 컬럼·컨트롤이 있는데 아무도 안 쓰는 상태

이번 사이클에 **세 번** 나왔다. 같은 실수다.

| 무엇 | 증상 | 고친 PR |
|---|---|---|
| `transactions.billing_month` | 021 이 만들고 라우트가 받기까지 하는데 **계산하는 곳이 없어 늘 NULL** | #415 |
| 기간 필터의 "자동 생성 내역 포함" 토글 | URL 만 바꾸고 **서버로 안 감**. 서버에도 받을 자리 없음 | #414 |
| `payment_methods.account_id` | 쓰는 곳이 없었다 | #378 |

**눌러도 아무 일이 없는 컨트롤은 없는 것보다 나쁘다** — 사용자는 데이터가 틀렸다고
읽는다. 새 컬럼·컨트롤을 넣을 때 **쓰는 쪽까지 같은 PR 에서 잇거나, 안 이으면
이슈로 남긴다.**

### 2.4 파생값은 자기 입력을 따라가되, 입력이 그대로면 건드리지 않는다

`billing_month` 를 PUT 에서 어떻게 다룰지에서 기존 테스트와 새 테스트가 **정면
충돌**했다.

```
settlementBackupRoundtrip D-4   메모만 고쳤는데 청구월이 지워지면 안 된다
settlementBilling C-4 · C-5     구매일·카드를 고쳤는데 옛 청구월이 남으면 안 된다
```

둘 다 맞다. `COALESCE` 로도 무조건 재계산으로도 한쪽이 깨진다. **입력(`date` ·
`card_product_id` · `settlement`)이 실제로 바뀐 경우에만 다시 계산**하는 것으로
풀었다.

### 2.5 조사(으로/로)를 하나로 박으면 반드시 틀린다

라벨 셋의 받침이 다 다르다 — `즉시 결제`(받침 없음) → 로, `카드 사용`(ㅇ) →
**으로**, `카드대금 인출`(ㄹ) → 로.

`client/src/lib/settlementLabels.js` 의 `withRo()` 가 받침을 보고 가른다. 화면이
라벨을 따옴표로 감싸 넘기므로 **따옴표를 건너뛰고 안쪽 한글**을 본다(첫 구현이
맨 끝 글자만 봐서 늘 `로` 로 떨어졌다).

금액 뒤에도 붙는다 — `3,000,000원 로` 가 떴다. 문장 구조를 바꿔(`N원 늘어요
(전 → 후)`) 조사 자리를 없애는 쪽이 낫다.

### 2.6 검사 도구는 자기 자신에 대한 반례가 있어야 한다

위임 검수 스크립트가 **워크트리 경로를 하드코딩**하고 있었다. 다른 워크트리에서
호출하면 `git diff` 가 엉뚱한 저장소에서 돌아 **모든 검사가 빈 diff 를 보고
통과**했다. 테스트를 12개에서 0개로 지운 파일이 `✔ 검수 통과` 로 나왔다.

**규칙: 검수 스크립트를 믿기 전에 알려진 나쁜 입력 하나로 `exit≠0` 을 확인한다.**
초록불이 "문제 없음" 인지 "안 보고 있음" 인지는 그렇게만 구분된다.

## 5. 하네스 — 로컬모델 위임

지표는 `.delegation-metrics/` 에 있다(저장소 밖, 로컬). `RATIO_20260805.md` 와
`issue-379/METRICS.md` 에 이번 사이클 교훈 16~19 가 기록돼 있다.

**이번 사이클 결론: 1파일 = 1호출.** 6개 배치는 24분에 대상 편집 0건이었고,
1파일씩 주니 첫 파일이 70초에 완전한 결과를 냈다. whole edit format 이 6개 파일을
통째로 재출력해야 해서 30b 모델이 감당하지 못한다. **배치가 빠른 게 아니었다.**

검수 순서를 고정했다.

1. **범위** — 배치 밖 파일이 바뀌었나 (`exit 1` 이면 라운드 폐기)
2. **내용** — 주석·테스트 수·`use strict`·포트
3. **실행** — `timeout 60 node --test <파일>` ← 상한 필수. 잘린 파일에서 영원히 기다린다
4. **사람** — diff 를 눈으로

라운드 10·11 이 이 순서의 필요성을 각각 실증했다(§2.6 참고).
